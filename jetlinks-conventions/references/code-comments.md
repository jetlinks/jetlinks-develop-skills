# JetLinks 代码注释规范

解释公共契约、业务原因和非显然边界，减少人和智能体反推意图的成本。只检查本次新增 / 实质修改的逻辑及已过时的相邻注释。

## 公共契约

- 新增或改变的公共类、SPI 与扩展入口说明职责、调用方 / 时机及关键限制；方法说明契约所需的参数、返回、错误与副作用。
- 订阅、回调、并发、事务、资源所有权或兼容限制若影响实现者，写入契约，不能要求读默认实现才能知道。
- `@since` 使用可验证的实际版本，`@see` 指向有帮助的相关类型或参考实现。版本未确认时先查构建 / 发布事实，不伪造；仅有必要且无法核实时才询问。
- 沿用已有准确契约，不为每个 DTO 字段和继承方法重复复制说明。

## 实现注释

在代码旁用简短说明解释下列非显然内容：

- 业务口径、动作前态、权限或独立信任边界为何在这里处理。
- 兼容对象、历史原因及退出条件。
- 事务提交时机、幂等 / 重放、顺序 / 并发、背压 / 批次与资源释放。
- wire / 序列化假设、异常转换和平台扩展限制。
- 追踪或 MBean 操作的特殊业务 / 安全约束。

复杂流程先按业务阶段命名，注释补充无法从名称和类型得出的原因。长篇设计归已有设计文档，代码保留必要边界及链接。

## 无需额外注释

简单赋值、直接 DTO 映射、标准继承 CRUD、显然的一步委派、普通模板展示，以及名称 / 类型已清楚表达的实现，不机械补注释。没有这些注释目标时直接继续，不逐文件输出“为何不写”。

不要逐行复述代码、保留过时结论、写无法核实的版本、把开发过程放进源码，或仅在最终回复 / PR 中解释应当留在代码旁的契约。
