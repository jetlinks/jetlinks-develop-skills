# JetLinks 根因处理与扩展边界

在工具、SDK、框架、公共组件或共享能力不能满足当前任务时使用。先定位缺口 owner，不把“能绕过去”当作问题已解决。

## 区分缺陷、缺能力与业务差异

| 事实 | 处理 |
| --- | --- |
| 公开契约已支持，但组件行为、类型、样式、状态或生命周期错误 | 通用组件缺陷：在所属仓库修复共同根因并提交 PR |
| 当前契约确实没有这项通用能力 | 评估正式扩展点、配置 / slot / hook、公开 API 或兼容的能力增强 |
| 场景具有不同且明确的业务语义 | 规则放业务 owner，保持通用组件契约；不是给公共层加入场景 ID 分支 |
| 使用方式错误、版本不符或装配缺失 | 修消费方式、版本或装配，不把调用错误当上游缺陷 |

先核验实际导出、目标版本、相邻用法和最小触发。缺少一个方便写法、一次报错或视觉相似不能单独证明组件有缺陷。

## 通用组件缺陷的闭环

1. 确认组件 owner、公开契约与最小复现，区分实现错误和契约缺口；保留用户目标及需要支持的同类场景。
2. 在组件所属仓库 / 模块修复正确抽象，覆盖原始触发与受影响的同类代表；按契约保持事件、状态、权限、可访问性、样式 token 和生命周期一致。
3. 调用方只接入正式修复，通过公开 API、正确依赖版本或仓库已有联调机制使用；不复制修复代码到业务侧制造第二实现。
4. 将修复提交到所属仓库的 PR。已有修复任务和发布授权直接复用；修复尚未可用、仓库不可写或缺少发布权限时，保留可审查补丁与具体阻塞，不把规避方案宣称为完成。提前共享按已授权 draft 流程处理，多个仓库的交付说明依赖关系。
5. 验证在连贯阶段集中完成；调用方与上游修复各验证其改变的契约，不对每次编辑构建。

禁止以业务包装、私有复制、深导入、DOM / CSS 强行覆盖、运行时 patch、绕过校验 / 状态 / 生命周期，或针对页面、产品、租户的分支掩盖已确认的通用组件缺陷。正常使用公开 slot、配置或设计 token 表达业务差异不属于规避，前提是组件本身正确且契约适用。

## 能力缺口的正式路径

- **封装 / 可见性**：查公开 API、SPI 或 owner 扩展，不用 setAccessible、Unsafe、库包名伪装或隐改可见性调用内部实现。
- **序列化**：复用标准 ObjectMapper / 序列化配置，通过 Module、Mixin、Serializer / Deserializer 等扩展；不新建平行配置躲开错误。
- **类型 / 依赖**：修真实类型、泛型和版本契约，不用宽泛 any、强制转换或不稳定依赖隐藏不兼容。
- **响应式**：修异步组合和适配边界，不靠 block、嵌套 subscribe、sleep 或全局状态协调。
- **错误 / 测试**：保留约定错误和业务断言，不静默 catch、printStackTrace、全局压制告警、关闭测试或改期望掩盖缺陷。

这些限制针对绕过契约的修补；框架自身正式的反射 / 元数据机制、合理局部类型抑制和已建模的业务策略，按其真实职责判断，不能仅因关键词误报。

正式路径仍不可行时，说明已验证限制、可审查方案和实际取舍；只有会改变已接受业务 / 安全 / 兼容契约或新增权限的决定才需询问。技能不扩大授权，也不以询问代替已可完成的 owner 修复。
