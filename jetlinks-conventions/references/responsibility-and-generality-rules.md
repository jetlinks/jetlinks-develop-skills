# 职责、语义与通用性

新增或调整组件 / 模块职责、公共抽象、业务语义、常量策略或初始化时读取。具体框架约定由对应技能拥有，不把此文件变成每次局部修改的必读清单。

## 职责与依赖方向

- 组件围绕稳定能力和不变量组织，按变化原因划边界。Controller 负责协议与入口，应用 Service 编排用例，领域能力拥有业务规则，仓储负责持久化；公共组件不理解应用专属对象、菜单、租户或部署场景。前端职责按 [web 代码组织](../../jetlinks-web/references/code-organization-rules.md) 判断。
- `core` / 公共契约不能依赖 `manager` / 运行时实现。低层解析、算法、协议或通用 UI 不反向依赖上层页面 / 编排类型；共享类型归语义 owner。不能只移动文件而保留循环依赖。
- “组件中已有一个开关关闭 Controller”不能证明管理职责属于该组件。公开 Web 管理入口、持久化、装配和可复用执行能力按职责放置，避免公共运行组件被迫加载管理端。
- 业务绑定、通用关系和本体组合有不同 owner。业务通过 relation / core 的公开契约及注解暴露事实与能力，不依赖 ontology；本体在上层消费。不复制关系注册中心、不双写同一事实；AI 推断 / 提及与已确认关系保持不同语义。实现选择归 [对象建模](../../jetlinks-boundary/references/object-modeling-rules.md)。
- 应用对平台实现的依赖与字段扩展遵循 [平台边界](../../jetlinks-boundary/references/application-platform-rules.md)，同部署不能放宽它。

## 抽象与复杂度

- 优先已有能力、普通函数、局部变量和职责清晰的私有方法。新增接口 / 策略 / 注册器 / 缓存须对应真实变化点、公开扩展需求或可核验成本；不为假想未来创建多套机制。
- 同类问题在契约、数据模型、默认策略或适配端解决。实验、协议或特定部署的可变逻辑留在其 owner，不污染通用生产接口。
- 删除纯复制转发、不可达分支、重复扫描和无消费结果；先确认生命周期、授权、快照、缓存一致性等差异，不能因“都做校验 / 缓存”就认定重复。
- 按职责和变化原因拆分，不按文件行数、方法数或算子数硬拆；巨型类是定位信号，空包装与跨文件跳转也会增加成本。
- 新增抽象要能解决当前存在的重复语义、独立生命周期 / 不变量、公开扩展契约或可核验成本；只有“以后可能用到”时不建框架。单一消费者也可能有合理边界，不能用次数否定必要封装。
- 可读性看能否顺着名称、数据与副作用理解业务步骤；优先命名关键中间结果与完整阶段，不把每个表达式拆成一个 helper，也不以少类 / 少方法为由压成嵌套长链。

## 语义与魔法值

- 名称表达业务意图、单位、范围和来源；区分身份与仓储主键、定义与实例、选中与生效、候选与确认、缺失与拒权。不用含糊的 `type/status/data/flag` 掩盖多套概念，也不为每个局部变量追求长名称。
- `find` / optional 查找可以无结果，必选执行边界缺少服务 / 命令应按契约报错；合法 `Mono.empty()`、`Mono<Void>`、空集合、未提交、显式 null 与失败不能统一转换。DTO、命令、存储和 UI 沿同一语义解释。
- 算法阈值、权重、重试 / 超时、批量与并发上限、状态码、业务标识必须可解释。优先平台常量、枚举、命名策略或已有配置，注明必要单位与取值依据；把 `37` 换成 `DEFAULT_LIMIT = 37` 并未证明策略合理。
- 同一预算 / 默认策略由一个 owner 计算并向下传递，不在多个阶段叠加隐藏倍数、覆盖顺序或 fallback。可诊断的 explain / 日志不参与业务排序与状态决策。
- 0、1、空集合、明确局部协议位置等直观字面量无需全部抽常量。只有真实部署 / 运维差异才引入配置，不为消除所有字面量制造配置中心或枚举；同值不同语义的预算不能因数字相同合并成一个常量。

## 数据契约与配置

- 同一字段从入参、DTO、命令、元数据、序列化到存储及 UI，保持类型、单位、精度、时区、枚举值与缺失语义。不要为方便 JSON 互转而丢失类型、日期、二进制、精确小数或安全上下文；先复用平台正式 codec / 转换能力。
- 未提交、null 清空、空集合、无权限、不适用和未采集不能被统一默认值覆盖。类型断言 / 强转不替代真实契约，未知类型按既有扩展或错误语义处理，不静默丢字段。
- 查询和响应使用稳定语义标识，文案沿统一 i18n / 枚举元数据；不把用户语言固定进全局缓存或跨服务定义，不让展示字符串成为业务判断条件。
- 公共配置按现有 Properties / schema owner 集中声明默认值、单位和作用范围；同一能力不散落多处 `@Value`、系统属性和硬编码默认值。局部不变常量不必配置化；插件 / SPI 的配置能力以实际消费者和版本为准。
- 元数据同步不等于远端可执行代码 / 写入权限；在线可编辑声明、依赖可装配、数据可读取和动作可执行分别核验。开发分支上的能力不能作为全部已发布版本的默认能力。

## 通用策略与场景特调

- 区分用户目标、明确实施约束与未经验证的解法建议；公共方案仅有当前样例支撑时，按 [扩大依据](../../systematic-solving/references/systematic-solving-rules.md#扩大依据的时机) 核对契约、成熟模式及反例。合法且明确的业务差异继续在业务 owner 表达，不用通用最佳实践抹平它。
- 禁止在共享能力中按客户名、业务 ID、产品、模块名、页面路由、样本题目或关键词硬编码特殊通道 / 权重 / 阈值来掩盖共同根因。
- 合法业务差异用明确领域规则、现有策略或配置表达，并放在业务 owner；有据可查的协议兼容不等于特调。新增扩展点需有实际消费者和稳定契约，不把一条特判包装成庞大插件框架。
- 通用组件缺陷按 [owner 修复与 PR](root-cause-and-no-hack-rules.md#通用组件缺陷的闭环) 完成交付，不在业务调用方加 wrapper、复制或按页面 / 产品 ID 规避。修复覆盖同类机制与反例，回归样本不能变成生产题库。
- 协议消息类型分派、合法状态转换、真实业务策略和已有版本兼容可以合理分支；判断依据是领域语义与契约，不能仅因出现 switch、ID 或 fallback 就认定特调。

## 初始化与默认数据

- 通用组件只初始化其运行必需的中性元数据 / 能力注册，不默认创建某行业的产品、设备、用户、租户、告警规则、指标模板或客户绑定。
- 业务必需的初始配置归该应用的迁移 / 安装流程；演示、样本和可选模板放显式导入 / 选装入口，不能随所有平台启动自动执行。固定标识若是正式公共契约可保留，客户实例标识不得伪装成平台常量。
- 沿既有版本迁移和幂等机制执行，区分首次安装、升级和用户已修改数据；不得每次启动恢复默认值、覆盖用户配置或重建已删除业务对象。不要为一个初始化需求另造迁移框架。
- 删除初始化代码前确认已安装数据、外部引用和升级路径；已有业务数据的迁移 / 清理由其 owner 负责，不能因禁止特调而自动删除生产实例。

校验范围与变化语义由 [CRUD](../../jetlinks-crud/references/common-crud-rules.md#校验范围与变化语义) 拥有；数据隔离不通过上述业务字段 / 默认值设计另建机制，见 [AssetsHolder](../../jetlinks-assets-permission/references/assets-holder-rules.md)。
