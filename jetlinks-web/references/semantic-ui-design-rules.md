# 企业应用的业务语义与交互表达

用于菜单规划、列表与详情设计、跨业务工作区、规则 / 流程和设置配置的整体方案。先确定业务含义与用户任务，再选页面和控件；普通局部改动不要求补建本体模型。页面分型见 [页面分型](page-pattern-decision-rules.md)，编辑和草稿行为见 [任务连续交互](task-interaction-rules.md)，组件职责见 [公共交互契约](shared-interaction-contracts.md)。本文负责“什么含义应如何表达”，不另立保存或权限协议。

## 依据与结论边界

有成熟的建模方法、企业设计模式和交互标准，可以形成项目统一规范；没有一种行业标准规定所有企业详情都必须“基本信息 / 操作 / 业务联动”三个 Tab，或所有本体都必须图形化。

| 依据 | 支撑的设计判断 | 使用边界 |
| --- | --- | --- |
| Sophia V. Prater：[Object-Oriented UX](https://alistapart.com/article/object-oriented-ux/)（2015） | 先识别用户认知中的对象、内容和关系，再组织上下文导航与动作；按任务重要性排序 | 设计方法，不把数据库表直接当对象菜单，也不替代任务研究 |
| SAP Fiori：[Object Display Components](https://www.sap.com/design-system/fiori-design-web/v1-145/ui-elements/object-display-elements) | 对象名称、数值与单位、业务状态、草稿 / 锁定等技术标记应有不同表达 | 企业设计系统实践；沿项目 token 和组件实施，不照搬 SAP 视觉或数量配额 |
| Carbon：[Data table](https://carbondesignsystem.com/components/data-table/usage/) | 表格服务查找与列对比，支持排序、局部展开、行操作和选中后的批量动作 | 不把表格当所有复杂业务的页面壳，也不把它变成通用电子表格 |
| Palantir：[Ontology overview](https://www.palantir.com/docs/foundry/ontology/overview/) | 对象 / 属性 / 关系与动作 / 函数分别承载业务认知与业务变化，统一供应用消费 | 产品架构参考，不是行业标准，不引入另一套 Foundry 存储或执行系统 |
| W3C：[PROV-O](https://www.w3.org/TR/prov-o/) | 实体、活动、参与者及实际使用 / 生成有不同含义，来源可追溯 | 语义标准；普通关联不自动成为因果或执行血缘，不要求全量 RDF 化 |
| OMG：[BPMN 2.0.2](https://www.omg.org/spec/BPMN/2.0.2/)、[DMN 1.5](https://www.omg.org/spec/DMN/1.5/) | 区分过程编排与决策建模，选择适合的流程结构或决策表 | 本文核对官方概述，未做规范全文符合性认证；项目子集不能宣称完整 BPMN / DMN 支持 |
| [通用交互依据](interaction-design-foundations.md)中的 Ant Design、WCAG / APG | 原位操作、渐进披露、反馈、键盘与可读性 | 对当前语义的具体控件实现施加约束，不决定业务模型 |

本文的页面组合与菜单示例是基于这些依据的项目设计规则，不是文献逐字要求。成熟规范可统一“语义、层级、行为”；布局仍取决于角色、任务频率、内容长度与容器。

## 一、先把内容分成不同的业务含义

设计时用当前契约做一张简短映射：当前对象是谁，哪些是自身信息、关联对象、观测事实、动作、规则和过程，用户这次要完成什么。无需为已有简单页面新增 schema 或填写冗长设计表。

| 业务含义 | 用户应看到什么 | 默认交互 | 不应混同 |
| --- | --- | --- | --- |
| 对象身份 | 业务名称、类型图标、必要时编号和位置上下文 | 名称进入对象；ID 次级、按需复制 | 技术 ID 不占据主标题；同名不等于同对象 |
| 自身属性 | 可读值、单位、枚举含义；按业务概念分组 | 偶尔维护可原位编辑，密集录入保留输入 | 业务状态、外部对象引用不能都当普通字符串 |
| 对象引用 | 目标名称、类型图标和明确进入入口 | 就近预览 / 进入，返回保留原对象与筛选 | 不能只显示外键；字段引用不重复生成关系边 |
| 业务关系 | “所在空间”“负责人员”“关联工单”等有方向的业务名称及目标集合 | 单个引用、紧凑列表、关系组；需要探索路径时用图 | 图上连线不天然代表调用、先后、控制或因果 |
| 观测 / 查询事实 | 值、单位、观测时间，必要时质量、来源与有效范围 | 查看、刷新、比较、钻取；历史值标明时点 | 无数据、读取失败、来源不可用、未知与正常分开 |
| 业务状态 | 有业务含义的短语，如待复核、处理中、已停用 | 能解释当前处境；状态允许的动作就近可见 | 不与选中、未保存、连接状态或请求 loading 合并成一个状态色 |
| 动作 / 命令 | “停用设备”“受理异常”等动宾名称、目标与必要参数 | 按真实影响确认，执行后显示原回执和后续去向 | 不用通用“编辑状态”绕开状态转移；受理不等于效果完成 |
| 规则 / 决策 | 适用范围、输入、条件、结果或动作 | 业务语句、公式、决策表与样本解释 | 不为一条条件强造流程图，也不将所有规则拆为字段表单 |
| 过程 / 事件 / 证据 | 发生内容、时间、参与者、原业务记录及结果 | 时间线 / 记录列表，必要时查看执行路径与依据 | 模型设计图、实际执行路径、关联图各有不同语义 |
| 配置及其生效范围 | 谁的设置、继承来源、当前值、覆盖和何时生效 | 局部草稿、验证、保存 / 应用 / 发布沿真实契约 | 个人展示布局不改变业务定义，保存草稿不代表运行生效 |

布局分组依据“共同回答一个业务问题、共同维护或共同影响决策”，而不是 JSON 嵌套、所属接口或字段数量。例如设备名称 / 编号属于身份；型号与位置属于识别上下文；温度及时间属于观测；所属空间属于引用；停机属于动作。

## 二、菜单规划：业务对象、工作任务和配置范围

全局菜单承载稳定、频繁、需要独立查找的目的地。对象关联和当前对象的动作优先在上下文中进入，避免沿部门、表名或微服务逐层找页面。

| 入口类型 | 合理表达 | 示例与边界 |
| --- | --- | --- |
| 业务领域 / 对象集合 | 稳定业务名称，支持检索和收藏视图 | 设备、客户、合同；独立管理的工单也可有集合入口，即使它同时出现在设备详情里 |
| 角色工作任务 | 用户要处理的集合，按职责与优先级组织 | 我的待办、异常处置、待复核；“全部对象”不能替代任务入口 |
| 探索与观测 | 明确的跨对象检索、关联探索或监测任务 | 资源浏览、运行监测；不要求普通台账先经过全局图谱 |
| 定义与设计 | 管理可复用的规则、模板或流程定义 | 规则库、流程模板；运行实例 / 待办与定义配置区分 |
| 设置 | 按组织、项目、对象或个人的作用域归类 | 项目通知设置、个人偏好；对象专属参数留在对象内 |

示意：业务管理下可以有设备、工单；工作台有我的待办、异常处置；自动化有规则和流程模板；系统设置承载跨对象的管理配置。这是可能的分组，不是固定菜单配额或要求新增这些入口。

一个对象保持稳定身份和规范详情入口，可从集合、关联或待办多路到达。进入时带入对象与任务上下文，返回恢复查询、分页和定位。菜单名用用户理解的名词或任务名；新增、导出、停用等是页面动作，不单列同级菜单。无访问资格、暂不可用和来源缺失按平台已有语义处理，不靠菜单隐藏代替授权。

## 三、普通台账类管理

**任务是查找、比较、维护一批同类对象。** 表格通常最直观，不应为了现代感改成稀疏卡片墙。

左分区＋右列表适合稳定分类、空间 / 组织范围、任务队列与常用视图。左侧负责缩小集合或切换稳定目的地，右侧承载查询结果及就近动作；不要把每条记录都塞进左栏取代集合列表。分类与状态等多个筛选维度应与主筛选共用条件模型，说明计数范围并提供还原入口；设置分区是内容目的地，不伪装成查询条件。打开详情及关联对象后保留原集合上下文，返回恢复筛选、分页和定位。窄容器可收起分区到抽屉，主列表仍可查找和进入，必要时表格内部横滚，不使整页横向溢出。实际组件组合见 [Core 场景](example-locations.md)，不要求所有页面都使用左右分区。

- 列表先呈现身份列，再放本次筛选 / 对比真正需要的状态、分类、归属和关键业务值；次要编号、描述、时间按阅读优先级弱化。数字和单位便于纵向比较，状态文字与颜色一致。列由任务决定，不展示所有实体字段。
- 名称进入详情，复选框选择批量对象，行内常用动作与“更多”各有清楚入口；不要让整行点击同时承担进入、选中和执行。批量动作出现时说明选择数量与范围，跨页选择按既有契约，不悄悄扩大为全部数据。
- 简短补充信息可展开行或侧区；内容复杂、需要长期停留或有独立 URL 时用完整详情。卡片适合缩略图、空间识别或少数对象的综合状态，不能只因“新 UI”而取代表格。
- 详情先明确身份和识别上下文，再围绕当前任务安排主要内容与辅助关系。共同维护的资料与说明归为一组；观测值与其时间、来源相邻；异常、规则、执行记录按真实关系分别命名。处置动作靠近其依据和处理过程。双栏应有主次职责，不能将资料、观测和关联列表任意分摊到两列；窄容器按相同业务顺序展开。少量信息用一个内容区；独立且频繁切换的子任务才用 Tab，长页也可用分区锚点，不为普通字段维护造单独编辑页签。
- 新建直接激活关键输入，按完整业务约束创建；创建后进入新对象。日常维护可原位编辑独立字段，必须一起校验的内容按一组修改。完整首次录入用表单仍合理。

例：设备列表突出名称、运行状态、型号、所在空间和最近上报。详情身份头显示名称与状态；“设备资料”将真实存在的型号、空间、位置、负责人和维护说明归为一组；运行观测就近呈现值 / 单位 / 时间与关联异常；关联规则呈现定义类型、发布状态与版本。少量内容沿一个阅读流接续，复杂内容再依据任务建立互补分区。没有的数据不补造。停用是动作，产品与空间是引用，读数不是可编辑的基础资料；关联规则不等于已触发该次异常。

## 四、复杂业务联动与多对象关联

**任务是围绕一件事理解关联对象、作出判断并推动业务。** 先选中心对象或当前事件，详情成为有上下文的工作区。

- 首屏回答“当前什么情况、关联谁、接下来做什么”。关键事实与下一步动作相邻；辅助证据、关系和历史按需展开，不能把信息散到多个管理菜单。
- 关系用明确业务名：告警的“发生设备”、工单的“负责人员”、合同的“所属客户”。目标显示业务名称和类型，集合按关系分组，有真实总量时才标总数；预览数量与集合总量分开。
- 根据问题选视图：核对属性用表格 / 详情，理解事件演进用时间线，探索多跳依赖才用关系图。图是任务视图之一，保持当前位置和已展开路径，不默认将全平台关系铺满首屏。
- 将“结构关联”“动作触发”“实际执行”“业务结果核验”分别表达。例如“设备属于车间”是结构关系；“告警触发通知”只有源记录支持时才是执行关联；“通知已发送”不能推出负责人已处理。
- 操作输入携带当前对象和已声明上下文，执行时核对实际目标与版本；目标或主体变化后失效旧确认。受理后显示工单 / 任务回执和办理入口；业务流程长时保持原业务 owner 的状态及权限，不在通用工作区复制办理系统。

例：从“泵房温度异常”进入，身份头标明该次告警和发生时间；主区显示当时测值与设备现状，旁边给出可执行的受理入口；关系区显示设备、所在空间与负责人；下方列出已关联工单和处置过程。缺少负责人或证据时明确缺失，不把未知变成“正常”或自动补出因果。

## 五、规则、决策与流程

先判断编辑对象是什么，不能一律采用节点画布：

| 任务 | 优先表达 | 必须看见的关系 |
| --- | --- | --- |
| 单条触发 / 条件动作 | “当…满足…则…”业务语句，少量参数原位修改 | 作用对象、条件、动作及执行范围 |
| 多条件组合与优先级 | 条件组、决策表或有序规则列表 | AND / OR、匹配策略、优先级和冲突 / 默认分支 |
| 公式或属性处理链 | 公式、连续处理步骤、输入与阶段样本 | 数据类型、单位、引用依赖与每步输出 |
| 跨角色、等待、分支、补偿等过程 | 流程 / 状态图及按选择出现的设置 | 先后、事件、分支、职责和失败路径 |
| 运行中的一次实例 | 当前进度、任务、输入输出、回执和时间线 | 已执行路径、阻塞原因与下一步可操作事项 |

定义编辑与实例办理分开；调试使用明确样本和版本，按节点或规则解释匹配结果，旧结果标记过期。未匹配、跳过、失败与未执行不混同。草稿、验证、发布和运行停用按真实能力分开，发布前说明作用范围和影响；不用“保存成功”暗示已经投产。只有真实副作用 / 业务要求需要确认时才增加确认，不给所有测试按钮加一层模态框。

“异常发生 → 受理 → 派工 → 整改 → 核验”可作为过程；“温度超过阈值则发送通知”首先是一条规则。流程节点可以调用现有对象动作，但节点位置和连线不能自行授予权限或创造执行契约。

## 六、设置与配置

**任务是理解一个设置的影响并安全改变它。** 分类围绕能力和作用域，标签应让用户知道改变后会发生什么。

- 首先标明作用域：个人 / 项目 / 组织 / 当前对象；继承值、默认值与本地覆盖可分辨，提供恢复默认或取消覆盖的明确含义。恢复和删除是不同动作。
- 少量独立偏好可直接切换并就近反馈；通知渠道、连接参数、联动策略等关联内容共享草稿，校验后按服务契约保存 / 应用。不是所有开关都即时生效，按实际边界表达。
- 顶层按业务能力分组，如“连接”“采集”“通知”；组内先放常用关键项，高级参数按需展开。高级区不能藏当前错误、必填项或会影响用户理解的生效条件。
- 只在对照输出有实际价值时使用右侧预览，如通知模板效果、采集试读或权限影响；少量字段不再复制一张摘要卡。长配置可保留分区导航和明确动作区，不为字段多强造向导。
- 类型或模式选择采用图标、主名称和短差异说明，选择后显示真实适用内容；切换时保留或清理不适用值需有明确业务约定。敏感值按原平台策略掩码和编辑，不用假默认值覆盖已有秘密。
- 远程验证、保存、生效和重启分别呈现；保存失败保留草稿，部分生效说明范围及可恢复方式。只有后端支持时才提供一键回滚。

例：通知配置先选当前项目，展示继承的默认渠道与本地覆盖；渠道卡只承载真实支持的渠道，选中后就地输入该渠道参数；右侧若存在就展示实际模板预览和测试回执。测试、保存配置、启用规则是不同动作。

## 七、其他常见场景

| 场景 | 主要表达 | 关键区别 |
| --- | --- | --- |
| 待办 / 审批 / 处置 | 按责任、优先级和期限排列的任务队列 + 上下文详情 + 可执行动作 | 当前任务与所关联的业务对象都可识别；流转动作不是普通字段编辑 |
| 监测与运维 | 当前状态、趋势、异常列表和可定位的对象 | 实时性、观测时间、数据质量明确；采样更新不抹掉当前选择 |
| 分析与报表 | 业务问题、时间 / 范围、结果图表与明细钻取 | 聚合口径、单位、来源和数据时点一致；图表有具体决策用途 |
| 内容 / 页面设计器 | 实际内容布局 + 选择锚点 + 按需设置 + 同定义预览 | 正文内容、设计属性、办理时可填 / 只读 / 隐藏属于不同语义，不退化为全量字段配置表 |

## 八、跨页面统一的表达语法

名称 / 图标识别对象；链接表示可进入；按钮表达动作；状态标记描述处境；表单编辑值；关系标签解释连接；时间线表达发生过程。不同语义不能只因样式相似而互换。

颜色区分当前选中、需要处理的业务状态与错误；草稿标记独立于业务状态。图标沿业务类型或动作统一映射，选项中主名称优先、说明次级且可读，简单枚举无需硬凑图标。强调大小来自决策重要性，不按数字大小自动猜测异常。

左右区由互补职责决定：列表 / 当前对象、内容 / 选中设置、规则 / 验证等。窄屏先保留当前对象与任务，再按依赖排列事实、编辑、验证和应用；需要列对比的表格可以有明确横向滚动，不强制丢失列关系。面板重排不重置草稿、选择、焦点或返回锚点。

## 九、与当前本体和公共能力衔接

本体语义指导信息架构，不要求所有页面依赖本体模块，也不从未标记的字段名猜测业务含义。目标版本的事实源与可用性仍按 [组件事实源](component-source-rules.md) 核验。

- 复用原对象身份和属性模型。当前 core 的对象能力区分 `property / query / action`，`valueType` 表达单位与枚举，`semanticRole` 与显式 `reference` 可提供身份及对象引用；这些是已有契约，不为 UI 再造一份对象协议。
- 以当前公开出口评估 `ObjectOverview`、`ObjectDataView`、`ObjectReferenceDisplay`、`ObjectCapabilityPicker`、`ObjectOperationPanel`。引用展示只发导航事件，动作面板消费原输入与回执，数据展示不自行请求。不能因组件名存在就假定当前部署已接通全部来源。
- 业务专属展示沿 `objectPresentations` 等已有扩展入口，稳定成员引用匹配，避免按设备 / 人员 ID 特调。状态含义、操作前置条件和异常等级由业务声明 / 适配，不从文案和数值猜测。
- 本体的 `definition` 与 `presentation` 分开；展示布局不能改变查询范围、授权或执行。模型发布版本、动作目标、证据来源和完成核验继续沿原契约。
- 来源关系、查询证据与执行血缘各自有明确含义；无来源记录不补造因果，`unknown / unavailable / noData` 不合并成成功。请求完成、动作受理和业务效果核验分层反馈。

以上核心语义已有来源，业务优先级、领域分组、默认首屏和复杂编辑器仍需要设计判断。先用现有组件和适配验证消费者，再按真实重复缺口公共化。不要现在新增通用 `SemanticPage`、自动菜单生成器或用一份 schema 生成全部企业应用。

## 十、方案与验收

一个可评审方案应让人看清：当前角色 / 任务、中心对象、语义分组、默认重点、菜单入口、列表选择依据、详情 / 编辑位置、动作范围及结果如何返回。用简短示意即可，不强制另建流程文档。

阶段验收走通真实任务：从入口找到目标，理解事实与关系，执行授权动作或修改，得到对应结果，并能返回原上下文；检查选项是否改变真实内容、加载失败和未知能否区分、窄屏顺序与键盘路径是否成立。整页嵌入按 [宿主契约](shared-interaction-contracts.md#原型进入平台统一宿主契约) 核对实际壳层、主题与内容状态。技术验证只证明相应实现契约，不能据此宣称用户效率提高。Core 中的 [场景入口](example-locations.md) 提供台账、业务联动、规则 / 流程、设置与监测点的本地可运行组合；具体范围见目标 core 的 `src/views/interaction-examples/semantic-scenarios.md`，本地交互不等于真实业务服务已接通。
