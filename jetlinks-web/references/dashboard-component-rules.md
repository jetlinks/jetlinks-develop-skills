# JetLinks Dashboard Component Rules

用于实现 `visDashboard` 运行组件、配置面板及设计器注册。普通表单、详情与配置交互参考 [Core 自包含场景](example-locations.md)，不要求参考或初始化可选业务模块。

## 核对当前接入契约

从当前 core 的 `src/components/DesignerPreview/`、`DashBoardCanvas/` 说明与真实调用开始，核验目标应用采用的运行组件注册、配置面板注册、分组发现与组件元数据合并方式。只沿本次接入所需的公开链路查找，不假定某个业务模块的扫描文件存在。

确认以下事实后再接线：

- 当前设计器如何获得运行组件、配置面板与默认配置；实际扫描范围、构建方式与目标版本是什么。
- 组件 `type` 是否稳定且唯一，缩略图命名是否与扫描契约一致。
- 组件是应用内部能力还是通过已声明的扩展入口接入；当前是否有 `componentScope.modules` / `extendComponents` 等配置，不能仅凭名称推定可用。
- 若改变默认组件分组，修改真正拥有分组发现的入口；只改展示示例或同名文件不能证明已接通。

## 组件组织

按目标工作区既有接入结构放置。一个常见结构如下，它是职责示意，不要求创建所有目录：

```text
<当前组件实现目录>/<Group>/
  manifest.json       # 仅当当前扫描契约使用分组 manifest
  shared.ts           # 分组共享类型 / 配置合并
  components/         # 有真实复用的展示区域
  hooks/              # 刷新、轮询、订阅与生命周期
  services/           # 请求与业务动作
  <Component>/
    config.ts         # type、默认配置与画布元信息
    index.ts          # 注册出口
    index.vue         # 运行组件
    Config.vue        # 配置面板
    <type>.png        # 仅当扫描契约需要
```

只在同语义结构真实复用或具有独立职责时抽组件，遵循 [代码组织](code-organization-rules.md)；不把每个图表都包装成一套完整层级。

## 运行与配置边界

- 元数据的 `name`、`type`、`componentProps.style`、`gridItem` 与业务配置键以当前设计器契约为准。默认值完整，配置类型集中声明，避免到处 `as any`。
- 常见注册出口包含运行组件、配置组件数组与配置元数据。大体积或按需显示的运行 / 配置组件可异步引入；实际导出名称和结构必须核验，不复制某个业务组件名作为契约。
- 运行组件按真实 props（常见为 `info`、`style`、`isEdit`）消费类型化数据；配置面板按当前 `configData` 契约修改草稿，不暗含整页保存。
- 参数转换与配置合并集中在明确 owner；请求封装在 API / service，响应式刷新、竞态、轮询与订阅放 composable，展示组件保持无外部副作用。
- 编辑态采用样例预览还是允许真实读数，由设计器真实契约决定；不把进入编辑器隐式变成生产执行或写入。
- 配置变化或卸载时清理轮询、定时器与连接；旧请求不能覆盖新的配置结果。

## 状态与容器

仅按实际能力提供加载、失败、无数据与编辑态；失败可在当前区域恢复，空态说明必要下一步。图表和地图的父容器必须有可用宽高，观察实际容器变化，而不只依赖窗口尺寸。

标题、时间范围、状态与动作按任务分层；跨组件统一交互见 [公共交互契约](shared-interaction-contracts.md)。不要为统一外观强制同一个卡片骨架、配置字段集合或刷新周期。

## 接入验证

在连贯阶段结束后核验本次改变的发现 / 注册 / 画布显示 / 配置回显路径；检查 type 与缩略图、加载 / 错误 / 空态、配置变化和卸载清理。只检查源码目录存在或单个组件能渲染，不足以证明设计器已发现它。

真实入口缺失时报告当前应用的接入缺口，不要求用户为了寻找参考安装其他模块。
