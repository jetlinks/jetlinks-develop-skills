# JetLinks Web Directory Structure Rules

本文件用于确定前端改动的代码落点，避免页面、API、hooks、store 放错层级。

## 适用范围

- 新增页面或模块能力时判断目录位置
- 判断能力应放 `jetlinks-web-core` 还是 `modules/*-ui`
- 模块入口、注册文件、资源组织调整
- 连续迭代导致同一功能目录持续新增组件、hook、service、util 或样式文件

## 常见结构（候选）

- `jetlinks-web-core/`：应用壳层与跨模块共享能力（路由、布局、公共组件、公共 hooks、公共 utils）
- `modules/*-ui/`：业务子模块（页面、模块 API、模块组件、模块 store、模块 hooks）
- 子模块入口常见为 `index.ts` + `register.ts`

## 落点决策

1. 跨模块复用能力优先放 `jetlinks-web-core`。
2. 单业务域页面、组件、API、store 放对应 `modules/<module>-ui`。
3. 页面优先放 `views/**/index.vue`，接口放 `api/**`，复用逻辑放 `hooks/**`。
4. 新目录按需创建，不为了“结构完整”额外造目录。

## 目录规模治理门禁

新增实现文件前先扫描目标目录。满足以下任一条件时，必须暂停继续平铺，先完成一次职责审查：

- 同一目录已有 20 个及以上实现文件；测试、快照、生成文件和纯资源文件不计入。
- 已形成 3 个及以上可独立命名的稳定职责域，例如入口编排、数据来源、筛选、映射、预览。
- 两个以上外部入口正在深引用目录内部文件，或不同职责域开始相互深层引用。
- 单文件 300 行门禁、重复结构或复杂业务编排已经触发拆分，继续拆分会让新文件仍堆在同一级。

触发后按以下方式处理：

1. 先列出目录的公开入口、职责域、跨域依赖和明确不改的行为边界。
2. 按职责域建立子目录，默认最多两级；不要为单个文件创建只有一项的目录。
3. 根目录只保留必要的 `index.ts`、`register.ts` 或框架约定入口；跨模块调用依赖稳定导出，不继续新增深路径引用。
4. 组件、组合式函数、工具和样式跟随 owning domain 放置；只有被两个以上职责域复用且语义稳定的实现才进入 `shared/`。
5. 迁移前先建立稳定导出，再分批移动并检查旧路径、循环依赖和无用导出，避免把目录治理变成行为重构。

若当前项目已有明确且一致的平铺约定，可以保留现状，但必须说明为何职责仍单一、深引用可控，以及继续平铺不会扩大维护成本；不能仅以“改动最小”为理由跳过审查。

## 约束

- 不要跨模块用深层相对路径直接引用内部实现。
- 不要把模块私有逻辑堆进 `jetlinks-web-core`。
- 不要改变现有模块加载机制（入口与注册模式）。
- 若实际目录约定与本文不同，始终优先跟随当前工作区真实结构。
- 目录拆分服务职责边界，不以凑层级或减少文件数量为目标。

## 自检清单

- 代码是否落在正确层级（core vs module）。
- 页面、API、hooks、store 是否遵循模块既有目录风格。
- 模块入口与注册是否保持可发现、可加载。
- 新增文件前是否检查了目标目录规模、职责域和外部深引用。
- 触发目录治理门禁后，是否先完成职责审查并通过稳定导出隔离内部结构。
