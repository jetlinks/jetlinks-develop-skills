# JetLinks Web Page Pattern Decision Rules

本文件用于按用户任务选择列表、工作区、内容设计、连续规则、关系设计或分步流等主承载。配置、设计器、规则编辑及表单感 / 分散交互问题结合 [任务连续交互](task-interaction-rules.md) 判断；不因接口提供 CRUD 就默认管理表格。

## 决策顺序

1. 先判断用户进入页面后的第一任务是什么；整体规划时按 [业务语义](semantic-ui-design-rules.md) 分清身份、属性、关系、动作与过程，不从 CRUD 接口或本体类型直接生成菜单。
2. 写出完成任务的连续动作，如“选择对象 → 调整规则 → 看结果 → 应用”；判断哪些操作必须一起完成，哪些内容只是按需查看。
3. 再判断主要内容是批量字段对比、单对象内容、业务语句、依赖关系、时序还是运行状态。
4. 确定选择锚点、编辑位置、结果反馈与提交边界，最后选列表、卡片、步骤、时间线或关系图。后端实体与接口数量不直接决定页面、Tab 或弹窗数量。

## 页面分型

### 1. 标准 CRUD 管理页

适用：
- 核心任务是批量检索、筛选、增删改查
- 用户主要面对的是一批同类对象
- 决策主要依赖表格字段，而不是复杂状态流

推荐结构：
- 搜索区
- 表格或卡片列表
- 批量操作 / 行操作
- 就近行操作与独立字段轻量编辑；完整新建录入或联动编辑才选择局部表单、弹窗或抽屉

避免：
- 为了显得丰富而额外堆概览卡、趋势图、排行榜
- 把新增、改名、开关、复杂配置一律收进全字段弹窗

### 2. 对象详情驱动页

适用：
- 用户主要围绕单个对象持续查看、编辑、排查、处置
- 关键问题是“这个对象现在怎么样、下一步怎么做”

推荐结构：
- 顶部对象摘要
- Tabs / 分区详情
- 相关记录、事件、日志、配置
- 侧边动作或固定操作区
- 连续切换对象时保留导航与当前选择，配置、预览和观测关联当前对象

避免：
- 先展示一堆与当前对象无关的全局指标
- 在列表、详情、配置和观测间反复跳转并重选同一对象

### 3. 工作台 / 处置台

适用：
- 用户进入页面是为了快速识别问题并执行动作
- 页面要同时承载待办、状态、风险、最近变化、快捷操作

推荐结构：
- 优先级信息区
- 待处理事项 / 异常区
- 关键对象列表
- 快捷入口与联动动作

避免：
- 没有动作承接的静态数据墙

### 4. 概览 / 监控页

适用：
- 用户核心任务是理解整体运行状态、趋势和异常
- 页面更像“感知与判断”，不是直接录入和编辑

推荐结构：
- 真正有意义的状态指标
- 趋势或分布图
- 异常聚焦区
- 钻取入口

避免：
- 没有来源和决策价值的数字卡
- 与监控任务无关的 CRUD 表单区

### 5. 分步流 / 向导页

适用：
- 用户必须按阶段完成配置、开通、发布、联动、审批等流程
- 阶段顺序与校验关系明显

推荐结构：
- Steps / 分段导航
- 阶段性表单或配置区
- 阶段结果与下一步动作

避免：
- 把强顺序流程压扁成一页杂糅表单
- 按字段分组或接口调用顺序硬造步骤；普通编辑必须反复上一步 / 下一步

### 6. 时间线 / 记录分析页

适用：
- 用户需要理解事件演进、操作历史、状态变化
- 决策依赖“先发生什么、后发生什么、为何变化”

推荐结构：
- Timeline / 日志流
- 过滤与定位
- 关键节点高亮
- 节点详情

避免：
- 用普通表格替代需要时序理解的场景

### 7. 内容设计工作区

适用：用户需要排布页面、清单、办理内容，调整某项内容的展示与使用方式。

推荐结构：可直接选择、添加和排布的内容预览 + 按选择出现的属性区 + 同一份定义的试填 / 预览。

避免：在独立字段表单维护内容，再维护另一份预览；无选择时常驻全部设置。

### 8. 连续规则编辑区

适用：用户需要理解并修改条件、转换、计算或处理规则，核心是语义关系而非字段录入。

推荐结构：完整可读的业务语句 / 公式 + 就地参数、引用与函数选择 + 就近样例结果。

避免：把一个表达式拆成多行“字段—操作符—值”表单，或每个片段一个弹窗。规则编辑区可嵌入对象工作区，无需单独新增导航。

### 9. 关系 / 依赖设计工作区

适用：输入、处理、输出或对象协作关系本身影响用户判断，需要理解结构与传播路径。

推荐结构：关系主区 + 上下文添加入口 + 选中项编辑 + 节点结果 / 回放。

避免：输入、计算、输出分开维护后靠用户记忆关联；无关系需求也强用画布；为编辑一个节点遮住整张关系图。

## 方案档案

表单、详情、配置及左右分区 / 自适应的实现样例统一见 [Core 场景](example-locations.md)。反复阅读维护的内容采用 [读写一体](task-interaction-rules.md#表单与详情的读写一体)，新建与维护沿同一内容布局，必要录入保持可发现；联动配置保留完整草稿。分区职责互补，按内容与容器宽度选择，窄容器按任务顺序重排而不重建状态；不固定全站栏数或只用屏幕尺寸判断布局。

新页面或主交互变化前记录一个紧凑方案；局部字段、文案、样式或 props 调整沿已知方案实施。可以留在当前回复或任务已有设计载体，不为此单独创建流程文档。

- 业务任务与连续路径：谁围绕什么内容做什么，何时完成。
- 首屏骨架与密度：用简短 ASCII 标出主区、导航及按需编辑 / 反馈区，业务内容首屏可见。
- 选择与编辑：选中什么、在哪里改、哪些独立编辑、哪些共享草稿与提交；切换后如何保留上下文。
- 反馈与动作：预览 / 试算 / 应用各作用于什么，结果落在哪里，主动作和低频动作如何分层。
- 语义与复用：状态 / 标签 / 图标锚点，待核验的组件族，参考中借鉴与不借鉴的内容。

事实支持一个推荐且用户要求实施时采用推荐方案；其他方案会实质改变主要操作路径且证据无法选择时，才给少量有结构差异的选项。不为凑选项重复画相似骨架。

## 选择校验

在确定分型前，至少回答：

- 这个页面最重要的一个任务是什么？
- 用户更像在“找对象”，还是在“处理对象”？
- 用户是否需要快速执行动作，而不仅仅是看数据？
- 如果删掉列表、图表、统计卡中的一个，核心任务还能否完成？
- 是否把一个完整任务拆成许多局部表单，或把独立任务塞进一张长表单？
- 修改与结果能否在同一对象上下文中连续完成，还是需要跨页面、弹窗或 Tab 重选？
- 是否按已接受原型实现了操作路径，而非只换布局后仍走旧流程？

硬触发：

- 先复用当前请求、既有页面和已接受方案中的目标用户、第一任务、成功标准与对象范围；只有缺失事实会实质改变页面契约或主要操作路径时才询问，未知项数量不构成门槛。
- 多个页面模式会实质改变主要操作路径且证据不能选择时，提出聚焦选项；已有明确推荐和实施授权时直接继续。

如果回答后仍不明确，先出线框图再实现。
