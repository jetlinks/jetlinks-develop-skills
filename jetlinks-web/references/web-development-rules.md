# JetLinks Web Development Rules

本文件承载新页面、主交互或业务体验设计规则。入口与局部改动路径见 [SKILL.md](../SKILL.md)；只查当前决策涉及的章节，不要求所有前端改动先读全文。

规则优先级：
1. 用户明确要求
2. 目标项目真实代码、导出、依赖和运行机制
3. 目标项目已经存在且可核验的架构与设计系统约束
4. jetlinks-web 通用规则
5. 当前目录下的场景参考文档
6. 相邻页面示例

发生冲突时，优先级高的规则覆盖低的规则。
所有“必须”规则都必须定义适用范围和例外。

## 任务分类

- 页面实现或改造：列表页、详情页、弹窗页、配置页
- 仪表盘组件：`visDashboard` 运行组件、配置面板、设计器接线
- 能力复用：组件、hooks、utils、包级能力选择
- 交互方案选择：标准管理表格、资产卡片台账、筛选工作台、对象详情工作区、主从详情、配置向导、资源选择器
- 目录落点：代码放 `jetlinks-web-core` 还是 `modules/*-ui`
- 状态治理：本地状态、路由状态、store、服务端状态边界
- 质量与类型：交付质量、TypeScript 风险控制
- 业务驱动体验设计：工作台、流程页、概览页、监控页、分步任务页、非标准 CRUD 交互
- 参考借鉴：相邻页面、相似业务案例、Ant Design 交互模式的受控参考

## 标准工作流

1. 从用户目标、已接受选择和相邻页面建立当前业务上下文；已验证的导出、i18n 和状态锚点未失效时复用。
2. 新页面、壳层或主承载变化按 [页面分型](page-pattern-decision-rules.md) 形成方案；配置、设计器、规则编辑及表单感 / 分散交互问题按 [任务连续交互](task-interaction-rules.md) 确定完整操作路径、编辑和反馈边界。沿用明确事实支持的推荐方案；只有会实质改变用户结果或主要交互路径的未决选择才询问。
3. 选择组件时按 [组件事实源](component-source-rules.md) 核验实际使用的共享层或项目层。新增抽象或职责变化时再按 [能力复用](capability-reuse-rules.md) 和 [代码组织](code-organization-rules.md) 判断边界；找到合适能力即停止扩搜。
4. 保持 Ant Design / Ant Design Vue 和项目约定；用真实业务数据与动作支撑信息区块，不借用无关场景的指标或流程。
5. 只加载当前实现涉及的其他规则，完成最小完整变更；连贯阶段结束后按变化的行为、类型和交互风险集中验证。

局部字段、文案、样式或 props 修改不触发整页重新分型、全域复用扫描、对未改函数的注释证明或重构。若该修改实际改变公共契约或主要交互，则只升级对应受影响边界。

## 业务优先，参考为辅

- 先回答“用户为什么需要这个页面、进入后第一件事要做什么、做完后如何离开”，再决定布局和交互。
- 参考的目的，是帮助补足信息架构、区块节奏、反馈方式和操作组织，而不是替当前业务做决策。
- 用户已接受的原型是当前范围内的交互依据；复用平台视觉规范与基础能力，不以相邻旧页为由恢复旧流程。组件、权限、数据和提交仍以真实契约为准，冲突时说明具体差异并保留可实现的交互意图。
- 只有当参考页面与当前业务在对象模型、任务目标、决策链路上足够接近时，才允许借鉴它的交互组织。
- 完全不同业务场景中的布局、统计卡、快捷操作、流程步骤、看板分栏、告警层级、审批动作等，不应直接照搬。
- 任何首屏数字、统计卡、图表、趋势、排行榜或快捷入口，都必须能回答“这个信息帮助谁做什么决策”；回答不了就删掉。
- 新版样例页面只用于提取方案、布局、组件组合和交互节奏，不复制业务字段、接口、指标、局部组件实现或样例数据。
- `jetlinks-project-ui-cli` 仅在用户明确要求参考时作为外部参考，不进入默认依赖链，也不能作为当前项目组件存在性的证据。

## 先建方案档案，再选组件

- **方案来源**：[`page-pattern-decision-rules.md`](page-pattern-decision-rules.md) 的页面分型 + [`component-reuse-patterns.md`](component-reuse-patterns.md) 的场景组件矩阵。
- 除非命中局部调整范围，否则方案档案是默认强制环节；不允许跳过方案档案直接落地传统 CRUD 套壳。
- 方案档案按 [页面分型](page-pattern-decision-rules.md#方案档案) 记录业务路径、首屏骨架与密度、选择 / 编辑 / 提交边界、结果反馈、语义与复用。核心组件族来自共享层和项目层，落地前仍要核验；一个可信推荐即可，不为凑替代方案增加讨论。
- 候选必须基于"用户进入页面后的第一任务"挑选；事实清楚且只有一个可信推荐时记录"默认采用推荐方案"并继续，关键事实缺失或两个以上方案同样合理时再让用户选择。
- 方案确定后按组件复用矩阵选择共享基础组件和项目级组件，保持业务路径稳定；编辑位置、信息密度与状态层级依任务决定，不把矩阵中的候选区块和布局当成硬性配额。
- 不要随机挑一个其他业务功能来直接搬，也不要把不同业务中的指标、流程和操作布局移植到当前页面。

## 通用组件优先复用

- 卡片、列表、详情、图标、动态编辑、筛选、抽屉、标签、状态和资源选择等常见场景，应先查 `packages/components/src/components.md` 的共享基础组件映射，再查 `jetlinks-web-core` 的项目级组件和相邻生产组合。
- 名称、标签、说明、备注、描述等轻量字段优先单项编辑；不要为了编辑一个字段打开完整表单。
- 单项编辑不意味着联动配置也逐项持久化。规则、公式、点位和设计内容在所属草稿中保持完整校验与提交；同一对象的主区、编辑区与预览共享状态，不拆成多个独立表单。
- 详情页按任务组合摘要、分区、局部编辑与关联记录；不要求每页凑齐区块，也不固定为“表格列表 + 弹窗编辑”。
- 详情页头部摘要区与全站编辑样式统一：遵循相邻详情页既有模式、[`component-reuse-patterns.md`](component-reuse-patterns.md) 的基线约束，以及本文件的轻量字段单项编辑原则。
- 整站编辑控件映射可与 [`component-reuse-patterns.md`](component-reuse-patterns.md) 场景矩阵对照；勿在页面自造项目已规定的控件组合。
- 功能介绍只服务最终用户理解能力、开通条件、配置影响和下一步操作，不展示开发说明、交互原理或原型标注。
- 写任何用户可见文案前，先识别功能的最终用户角色（运营 / 运维 / 平台管理员 / 租户管理员 / 设备管理员 / 业务管理员 / 终端使用者 / 开发集成方等具体角色）、用户目标动作、用户能看懂的术语和下一步；优先复用当前请求、相邻文案和已接受设计；只有缺失信息会改变实际文案含义或用户动作时才询问。
- 禁止把用户的原始需求文本、prompt、内部任务描述、需求文档原文或开发故事卡描述直接放进页面文案、说明卡、Tooltip、空态、帮助区域或弹窗描述；必须按最终用户视角重写，动作动词开头，少用"用于 / 旨在 / 通过 / 借助"等需求文档口吻。
- 文案以目标用户的任务为准：设备接入、API 配置、运维排障等界面可准确展示必要的字段 key、API 路径、Topic、命令 ID 或权限码，并提供所需解释与操作。无关内部实现标识，以及 "TODO / 占位文案 / 待接接口 / 原型说明 / 设计意图" 等开发过程字样不进入最终界面。
- 空态 / 错态 / 加载态文案要具体到对象与下一步动作，例如"暂未接入设备，先创建一个产品再添加设备"；校验文案给具体限制和示例；提交反馈要带对象名与影响范围，而不是"操作成功"。
- 辅助说明就近呈现或进入帮助入口，关键限制、错误和任务必要说明保持可见。Tooltip 不承载唯一的关键信息，Popconfirm 仅用于需确认的动作；同一介绍不在多个位置重复。
- 如果不复用现有组件，必须说明已核验的导出入口、相邻页面和具体能力缺口。

## 何时需要用户决策

先从当前请求、已接受方案和现有页面补齐目标用户、第一任务、成功标准、操作对象与数据来源。只有剩余未知会实质改变页面契约、主要操作路径或信息含义时，才提出聚焦问题；未知项数量不是暂停阈值。

明确实施授权持续有效。用户已选择方案，或事实足以支持一个推荐时直接继续；进度询问、压缩恢复和普通局部调整不触发再次选择。未决部分不妨碍独立且已授权的工作推进。

## 原型只用于对齐，不进入最终界面

- 线框图、效果草图、信息架构草图的用途，是帮助开发者、产品和用户确认方向。
- 最终页面是给终端用户使用的，不是给开发者阅读设计思路的。
- 因此不要在最终界面中展示诸如“交互方式”“设计原理”“交互说明”“这里展示 xxx”“待接接口”“后续扩展”“模块说明”等原型或开发标注。
- 若确需说明复杂交互，优先通过自然的文案、控件状态、空态提示、帮助信息、Tooltip 或引导流程表达，而不是把设计备注直接渲染到页面上。
- 在线框阶段可以暂时用标注辅助沟通；一旦进入正式实现，这些标注必须清理掉或转换为真正面向用户的界面文案。

## 用户可见文案统一走国际化

- 页面标题、区块标题、字段展示名、表格列头、按钮文案、Tab 名称、占位文案、空态/错态提示、Tooltip、帮助信息、校验消息、枚举显示值等，只要最终用户会看到，就应优先走当前工作区既有 i18n 机制。
- 不要在页面组件、schema、columns、常量表或渲染函数里到处散落硬编码中文或英文文案。
- 如果当前工作区的 i18n 抽象支持默认值或 fallback，可以使用中文作为默认展示文本；但最终仍应通过统一的 i18n 入口取值，而不是直接把中文写死在页面结构中。
- i18n 以当前任务的 core 机制与业务约定为准，需要时结合 `$jetlinks-conventions` 判断落点，不通过参考可选模块再造另一套封装。
- “字段名不要写死”指的是字段展示名、列名、标题、按钮和提示文案不要散落硬编码；接口字段 key、路由参数 key、查询参数名等技术契约仍以真实接口和相邻实现为准。

## 后端枚举渲染

- 后端字段来自 `EnumDict` / `I18nEnumDict` 时，默认按 `{ value, text }` 处理。
- 表格、卡片、详情、Tag、Badge、Tooltip 和筛选 Token 显示 `text`，不要直接渲染整个对象。
- 表单 model、查询参数、路由参数、状态颜色、图标、排序、权限判断使用 `value`。
- 后端已经返回 `text` 时，前端不再重复维护枚举文案映射；如需颜色 / 图标，只按 `value` 建稳定映射。
- 同一字段可能返回字符串或对象时，集中 normalize，不在模板里到处写三元表达式。
- 条件筛选中的枚举字段优先走 `ConditionFilter` 的通用选项能力，支持 `loadOptions` 和 `loadSelectedOptions`，确保 URL 只存 `value` 也能回显 `text`。

## 交互与视觉优化

- 仅当任务包含页面美化、交互优化、层级梳理、状态页完善或体验打磨时，才进入本节规则。
- 优化前必须先从当前工作区提炼具体样式锚点：Ant Design / Ant Design Vue 组件语言、排版密度、间距尺度、色彩和状态色、圆角/阴影、按钮和表单反馈、表格操作区、弹窗/抽屉/Tabs 行为、图标和动效语气。
- 仅视觉打磨时，在当前 Ant Design 体系内调整层级、反馈和微交互，不额外改页面骨架；用户已要求交互重构或按原型实现时，按接受方案调整骨架，仍复用平台 token、尺寸、组件与主题。
- 当页面壳层或交互方案仍未定时，先建立方案档案；事实清楚时默认采用推荐方案，结构仍有分歧时让用户在少量贴合业务的方案中选择，不要直接把“管理页”当作默认壳。
- 页面交互方案选择只决定业务结构、信息层级和操作路径，不直接决定搜索组件；搜索层仍应单独判断是否优先使用 `ConditionFilter`。
- 页面交互方案选择不替代组件核验；选定方案后仍必须回到当前 workspace 的 `@jetlinks-web/components` 映射/导出、`@jetlinks-web-core/components` 导出，以及 hooks 和 utils。
- 先确认页面是否真的适合 CRUD 范式；只有当页面已被明确判断为标准管理页时，才进入管理页组合判断。
- 对标准管理页，若 workspace 已提供 `ConditionFilter` 与路由编码/回显工具，默认优先采用 `ConditionFilter` + `j-pro-table`；只有窄改旧页、用户明确要求旧表格风格，或搜索只是轻量固定表单筛选且无路由回显 / 远程枚举或引用选项 / 保存搜索需求时，才回退到 `ProSearch`。
- 使用 `ProSearch` 的例外必须具体：窄改旧页、用户明确要求旧表格风格、或筛选只有少量固定字段且无路由回显、远程枚举/引用选项、保存搜索、快捷筛选联动需求。相邻页面仍在用 `ProSearch` 只能作为兼容证据，不能让新页面默认沿用原始表格风格。
- 标准管理表格页不是“信息不足时的默认方案”。如果第一任务不是批量检索和轻量增删改查，或对象状态识别、持续筛选、处置流、单对象理解更重要，应优先走资产卡片台账、筛选工作台、对象详情工作区、处置工作台等方案。
- 如果核心价值在监控、分析、流程推进、异常处置或对象关系理解，优先考虑工作台、主从详情、分步流、时间线、卡片区块、图形化概览等更贴近业务的结构。
- 可以参考相似业务的设计，但必须先说明“为什么这个参考与当前业务相似”；只借鉴有业务对应关系的分区、交互和状态呈现，不照搬完全不同场景的交互动线。
- 优先优化信息层级、区块节奏、反馈状态、空/错/载态、微交互和可读性；不要平地起楼式替换成熟页面组合。
- 表单感与分散交互按 [任务连续交互](task-interaction-rules.md) 检查操作路径、语义控件和反馈闭环，不能只去边框、缩按钮或把长表单拆成多个小表单。图标 / 颜色统一语义，菜单展开态与选中值分别设计。
- 除非用户明确要求大改版，否则不要新增脱离现有框架的字体体系、品牌主色、背景装饰、重型动效或陌生组件语言。
- 不要为了让页面“看起来丰富”而堆叠无业务意义的统计数字、假趋势图、无来源占位数据或纯装饰卡片。
- 当需求描述不足以支持页面结构决策时，优先问清楚；当文字讨论成本高时，优先提供低保真线框图、信息架构草图或效果预览帮助用户确认方向。

## 核心约束

- 不要发明不存在的组件契约、hook 签名或 utils API。
- 不要绕开已有 `@jetlinks-web/components` 共享基础组件、`@jetlinks-web-core/components` 项目级组件或其他 `@jetlinks-web` 能力重造同类实现。
- 不要把 `jetlinks-project-ui-cli` 当成默认依赖、默认导入来源或当前项目组件存在性的证据。
- 不要在业务模块里重复手写 `@jetlinks-web/components` 已有的共享基础控件，或 `jetlinks-web-core` 已有的项目级卡片、详情、抽屉、标签、轻量编辑、资源选择和筛选组件。
- 不要把文档中的能力名称当作固定事实，必须以当前工作区导出为准。
- 不要在页面内硬编码路由权限、菜单元数据、API base 或 token 行为。
- 不要在组件内硬编码设计值；颜色、圆角、阴影、字号、字体、间距和局部尺寸优先复用 Ant Design Vue 能力与 `jetlinks-web-core/src/style.css` 变量或工具类，字号必须使用字号变量或组件默认字号，确实没有 token 可用的自定义局部尺寸统一按 `16px` 基准写 `rem`。
- 不要把一次任务扩展成大范围结构重写，优先最小改动、可验证交付。
- 不要把未经选择的外部灵感直接覆盖到 JetLinks 页面；沿用平台设计系统，在当前范围内落实用户已接受的交互方案，相邻旧页不高于用户选择。
- 不要因为实现方便就把业务页面压缩成老套的“筛选 + 表格 + 弹窗”后台 CRUD 套壳，除非当前业务和相邻实现都明确证明这就是最合适的结构。
- 不要默认表格 + 全量编辑表单；对象详情应优先考虑摘要、分区、局部编辑和关联记录。
- 页面确有通用条件搜索任务时按 [ConditionFilter 规则](condition-filter-rules.md) 选择搜索能力；不因新增页面就强加搜索区，也不默认以 `ProSearch` 完成页面生成。
- 不要把后端 `EnumDict` / `I18nEnumDict` 返回的 `{ value, text }` 直接渲染成对象，也不要为了显示文案在前端重复维护一份枚举文本映射。
- 不要在页面壳层或风格仍未收敛时，跳过方案档案直接默认传统 CRUD 管理页。
- `ProSearch` 的旧页兼容、用户明确选择与轻量固定筛选例外统一见 [搜索规则](condition-filter-rules.md#核心原则)；相邻旧页使用它不单独构成新页面采用依据。
- 不要把完全不同业务场景中的交互路径、快捷操作、状态组织或统计模块直接搬过来。
- 不要添加无来源、无决策价值、无后续动作承接的数据展示，只为了填满页面。
- 生产统计卡、图表、趋势和排行榜须有数据源、刷新与用途；明确请求的交互原型可按 [区块准入](block-admission-rules.md#原型与生产的边界) 用代表性样例验证。
- 不要在页面组件、schema、columns、按钮配置或状态映射里散落硬编码用户可见文案；统一走现有 i18n 入口。
- 不要把原型图中的说明文字、交互原理、占位备注或开发者导向文案渲染到最终页面；这不禁止在源码中为函数职责、关键业务逻辑和兼容边界添加代码注释。
- Vue/JSX/TSX 文件按职责边界抽离，不按行数机械拆分：职责混杂、持续膨胀时拆到子组件、hook、service 或 util；禁止为了降行数而抽离，形成 a > b > c > d > e 式超长包装调用链，扁平调用链的可读性优先于单文件长度。
- 新增文件时按 [目录规则](directory-structure-rules.md) 检查实际职责与依赖；仅调整已知文件不触发全目录治理，文件数量不单独构成迁移理由。
- 新增组件、hook、service 或 util 前必须先查已有能力；能复用或配置扩展时，不新增平行实现。
- 页面 / 容器组件只保留布局组合、方案级状态展示和命令分发；展示组件只通过 props / slots / 语义 emits 承载独立 UI；请求、参数组装、业务编排、复杂计算按 [`code-organization-rules.md`](code-organization-rules.md) 下沉到 composable/hook、service/api 或纯 util/mapper；交付时只说明本次实际新增或改变的职责边界与关键抽离决策；局部修改无需逐文件汇报未变职责。

## 按当前变化选择的自检问题

- 是否已核验目标能力在当前工作区真实存在。
- 是否先完成了业务目标、目标用户和关键任务路径分析，而不是直接套用后台管理页模板。
- 是否坚持了“业务优先、参考为辅”，并只借鉴了相似业务中真正适配的部分。
- 是否优先复用了现有组件、hooks、utils 或 store 契约。
- 是否已按页面分型规则建立业务交互方案档案、明确确认模式，并保持方案稳定。
- 对配置 / 设计器 / 规则编辑，是否在同一任务上下文完成修改、预览和提交，保留选择与草稿，避免跨弹窗或 Tab 重复操作。
- 是否将卡片、列表、详情、图标、动态编辑、筛选、抽屉、标签和资源选择映射到了 `@jetlinks-web/components` 共享基础组件或 `@jetlinks-web-core/components` 项目级组件。
- 是否通过 `packages/components/src/components.md` 按需找到共享组件文档，并用 `components.ts` 核验了根导出与目标版本。
- 如果没有复用两层现有组件，是否给出了可验证的映射文档、导出、相邻样例和能力缺口证据。
- 是否保持了模块边界、目录风格和页面交互一致性。
- 新增文件是否放在合适职责域，是否避免扩大深引用与依赖耦合；需要治理时是否限制在受影响范围。
- 每个新增或修改文件是否有明确职责，具名函数是否落在匹配的组件、composable、service/api 或 util/mapper 层？
- 新组件是否具备独立 UI 语义、状态 / 生命周期或真实复用价值，且没有无职责包装和过度透传？
- 是否避免用固定行数、props 数量或组件层级作为机械拆分依据，并保持调用链可读？
- 是否先抽取并遵守了本地样式锚点，而不是另起一套视觉体系。
- 页面里的统计数字、图表、概览卡和快捷入口是否都具备清晰业务含义、真实来源或明确动作承接。
- 是否已清理原型阶段的说明标注、设计备注和开发者导向文案，只保留终端用户真正需要看到的内容。
- 用户可见标题、字段展示名、列头、按钮、状态和提示文案是否统一走了当前工作区 i18n 机制，并在需要时提供了中文默认值。
- 如果需求存在关键不确定性，是否先向用户确认，或先提供了线框/效果草图帮助对齐。
- 是否完成了关键交互、状态流、路由权限和类型风险验证。
- 有原型时，是否在连贯阶段结束后对照关键状态与完整操作路径，核对按钮 / 菜单、就地编辑、结果定位及窄屏，而非仅凭静态截图声称还原。
