# 系统性求解规则

本文件把“不要反复特调”转换为可观察、可执行的求解门禁。核心不是禁止迭代，而是要求每轮迭代都由新证据推动，并在局部假设失效时升级问题模型。

## 1. 触发判断

### 主动进入

命中任意两项时，按复杂任务处理；单项本身属于高风险时也可直接进入：

- 改动跨模块、跨进程、跨前后端或跨两层以上架构边界。
- 真实行为由事件、命令、订阅、异步时序、缓存、权限、协议或外部依赖共同决定。
- 需求存在多个合理契约，或关键事实不能从当前代码直接确认。
- 涉及并发、事务、幂等、生命周期、状态一致性、兼容 / 迁移、性能、安全或数据权限。
- 需要同时协调多个调用方、实现类、数据形态或平台差异。
- 局部修复可能改变公共 API、SPI、数据模型、Topic、Command、Event、协议或通用组件。

### 强制重构

命中任意一项，停止追加局部修改，回到问题建模：

- 同一验收信号在一次实现后仍失败。
- 修复 A 后，失败转移到同类输入、另一个实现类或相邻模块。
- 下一步准备增加新的场景判断、fallback、重试、mock、兼容别名、隐藏开关或复制实现。
- 连续两个操作没有增加能区分候选根因的新证据。
- 测试只能通过弱化断言、扩大 mock、跳过真实边界或改低业务期望。
- diff 持续扩大，但无法用一个稳定不变量解释为什么这些修改属于同一解法。

以下不单独计为一次局部实现：同一完整方案中的导入、语法、格式、类型拼写、显然的装配遗漏，以及由同一个编译反馈直接指出的机械修正。若机械错误持续出现并暴露接口设计不匹配，仍应升级重构。

## 2. 问题框架

动代码前回答以下问题，答案保持简短并以工作区证据为准：

| 字段 | 要回答的问题 |
| --- | --- |
| 可观察目标 | 用户或系统最终能观察到什么成功结果？ |
| 当前失败 | 哪个输入、状态、时序或边界下出现什么结果？ |
| 不变量 | 无论场景如何变化，哪条业务 / 技术约束必须成立？ |
| 变化轴 | 不同实现、协议、租户、权限、状态、版本或输入之间真正允许变化的是什么？ |
| 影响面 | 谁生产、传递、转换、存储和消费这份状态或契约？ |
| 非目标 | 哪些行为明确不应借机重构或改变？ |
| 验收信号 | 哪些测试、日志、返回、状态或指标能证明目标达成？ |

“让当前测试通过”“给这个 ID 加个判断”“再兜底一次”不是不变量。把它们继续追问到业务语义、公共契约或生命周期责任。

## 3. 证据与假设

### 证据优先级

1. 可重复的失败、调用栈、运行时状态、真实输入输出和最小复现。
2. 当前工作区的生产调用链、测试、配置、版本和历史变更。
3. 同域相邻实现及其明确契约。
4. 官方文档、依赖源码、公开 API / SPI 和版本说明。
5. 外部成熟项目的同类做法。
6. 模型记忆或泛化经验。

低优先级证据不能覆盖高优先级事实。相邻代码只能证明“当前存在这种做法”，不能单独证明它正确或适用于所有变体。

### 假设账本

复杂任务至少保留两个仍然合理的候选，直到证据排除其中之一。假设账本属于任务运行态：Trellis 项目使用本地 task / research / runtime artifact；其他项目使用经 Git 忽略验证的单一运行态文件。排除假设后压缩或移除其过程细节，只保留理解当前决策所需的证据；不要把账本写入权威设计文档。

| 假设 | 已解释证据 | 若为真应观察到 | 最小区分检查 | 结果与决策 |
| --- | --- | --- | --- | --- |
| H1 | 现象 / 代码事实 | 可证伪预测 | 一次查询、测试或源码检查 | 保留 / 排除 |
| H2 | 现象 / 代码事实 | 可证伪预测 | 一次查询、测试或源码检查 | 保留 / 排除 |

检查必须能改变下一步决策。不能区分候选假设的重复搜索、重复构建或重复阅读不算进展。

## 4. 系统扫描

只扫描回答当前假设所需的范围，但要覆盖完整执行路径：

当路径跨多个 symbol / module、调用方不明确或需要变更影响分析时，按 `$jetlinks-code-navigation` 的检索漏斗建立有界多证据图：先精确 Git / 文本 / build facts，再符号语义和 1–2 hop 图查询，最后才升级领域抽取或数据流 / runtime。图中的 inferred / ambiguous edge 不能单独支撑高影响修改。

1. 入口：用户动作、API、命令、事件、Topic、定时任务或协议报文。
2. 所有权：哪个模块拥有业务语义，哪个模块只负责传输或适配。
3. 转换：DTO、Entity、消息、序列化、查询条件、权限上下文如何变化。
4. 状态：创建、更新、提交、缓存、发布、重试、清理和关闭发生在何时。
5. 变体：接口实现、产品 / 协议、平台、租户、角色、数据形态和版本差异。
6. 消费者：谁依赖当前契约，哪些属于已发布或持久化事实。
7. 观测：现有测试、日志、TraceHolder、MBean 或指标在哪里能看到真实行为。

画图不是强制动作。只有跨三个以上边界或线性描述容易丢失状态时，才用简短流程图或表格。

## 5. 选择解法层级

| 问题类型 | 识别信号 | 正确解法层级 | 禁止漂移 |
| --- | --- | --- | --- |
| 局部缺陷 | 契约正确，单处实现违反，兄弟实现正常 | 修正局部实现并补回归 | 借机抽象整个子系统 |
| 共享能力缺口 | 多个场景会以相同机制失败 | 公共契约、默认实现、适配层、扩展点 | 在公共层识别当前场景 ID |
| 合法业务差异 | 场景确有不同语义且变化轴稳定 | 显式策略、能力、配置、权限动作或业务条件 | 隐藏 if / fallback / 魔法值 |
| 契约错配 | 生产者与消费者对类型、时序、错误或生命周期理解不同 | 修改契约或边界适配并更新所有调用方 | 两边各补一个临时兼容 |
| 架构 / 发布决策 | 涉及模块责任、外部 API、持久化或迁移 | 给出方案与代价，用户确认后实施 | 把重大决策伪装成小修 |

抽象的边界由证据决定：至少确认一个同类代表场景或明确的变化轴；不要为了“以后可能用到”制造通用框架。

## 6. 局部修补预算与停滞协议

### 预算

- 同一根因假设下，只允许一次尚未验证的局部实现。
- 第一次验证失败后，先比较失败签名：输入、异常、调用位置、状态、时序和受影响场景是否相同。
- 只有新证据推翻或收窄旧假设后，才能进入下一轮实现。
- 第二轮不能只是把第一次的条件、fallback、mock、重试或兼容范围扩大。

### 停滞处理

1. 停止编辑并保留可恢复的当前状态，不用更多改动掩盖失败。
2. 在任务运行态中更新“预期—实际—新增证据—被否定假设”，替换上一轮失效状态，不追加阶段总结。
3. 检查是否漏掉调用方、变体、生命周期阶段、发布边界或真实数据形态。
4. 重新列出候选假设和区分检查。
5. 判断解法是否应从局部实现升级到共享能力、显式策略、契约或架构层。
6. 若升级会改变用户范围或外部契约，向用户说明证据、选项和推荐；否则继续完成重新建模后的闭环。

命令本身失败时也遵循同一原则：同一命令因同一原因连续失败一次后，先诊断环境、参数、权限或依赖；不要原样反复执行。

## 7. 实现闭环

以垂直闭环拆分工作，而不是把一个问题切成许多互不验证的微补丁：

1. 先确定契约、不变量和所有权。
2. 再修改最接近根因的公共点或局部点。
3. 同步更新受影响的调用方、配置、测试和文档契约。
4. 删除被新方案替代的 fallback、旧分支、临时 flag、重复实现和弱断言。
5. 在一个连贯阶段结束后统一编译 / 类型检查 / 测试，不在每次搜索或单行编辑后构建。

“最小完整改动”允许修改多个文件；“最小 diff”若留下两个契约、重复实现或下一轮必修问题，仍是不完整方案。

如果上述过程产生了稳定契约或架构结论，用户确认后再原位更新其权威来源；扫描、失败、假设演进、执行顺序和验证流水不随之提升。

## 8. 分阶段验证

| 阶段 | 验证目标 | 推荐证据 |
| --- | --- | --- |
| 建模完成 | 复现可信，假设可区分，影响面明确 | 最小复现、调用链、关键源码 / 契约 |
| 契约 / 骨架完成 | 类型、装配、公共签名一致 | 编译、类型检查、静态检查 |
| 行为闭环完成 | 根因已修复且业务不变量成立 | 定向单元 / 集成测试、真实数据样例 |
| 交付前 | 同类场景和既有行为未退化 | 模块测试、必要的集成 / 端到端 / 性能验证 |

每个阶段通过后，先以一个本地 commit 固化该阶段，再按 [`../../jetlinks-router/references/context-recovery-rules.md`](../../jetlinks-router/references/context-recovery-rules.md) 用实际 commit hash 更新 Recovery Capsule；阶段内部不按文件或步骤频繁提交。若暂停或上下文压缩发生在提交前，只把当前阶段记为 in-flight，不得写成已验证提交。所有阶段完成前不 push、不创建或更新 PR，除非用户明确要求共享中间分支或提前开 draft。

共享能力变更的最小验证矩阵：

- 原始触发场景：证明问题确实消失。
- 同类代表场景：证明不是对单一样例特调。
- 反例 / 边界：证明没有把不应合并的业务差异抹平。
- 既有回归：证明主要消费者仍遵守原契约。

不能执行某层验证时，给出缺失条件、精确待执行命令、替代证据和剩余风险；不要用更多 mock 宣称等价覆盖。

## 9. 常见失败模式

- **挤牙膏式 if**：每出现一个样例就加一个分支。改为识别稳定变化轴并建模策略或配置。
- **软特调**：不写具体 ID，但用输入形状、类名、异常文本或调用顺序暗中识别场景。它仍是特调。
- **测试牵引错误方向**：不断修改实现去追逐一个未经验证的测试假设。先确认测试是否表达真实契约。
- **只看失败文件**：忽略生产者、消费者和公共默认实现。沿完整路径查所有权。
- **无限搜索**：继续搜索相似代码但没有新决策。改用能排除假设的定向检查。
- **过度抽象**：一个局部 bug 被扩成通用框架。只抽象已证明的共同不变量和变化轴。
- **把重试当恢复**：没有幂等、退避、退出条件和观测的重试只会延迟暴露根因。
- **把兼容当保险**：未发布中间形态保留双轨实现。按发布边界收敛到单一 canonical 契约。
