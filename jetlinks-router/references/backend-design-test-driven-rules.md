# 后端设计与测试驱动规则

本文件组织 JetLinks 后端设计与验证：先明确本次改变的行为和验收，再按连贯阶段实施。任务契约可以直接来自用户已明确的请求、已接受设计或当前任务上下文；只有实质未决选择需要新增确认。

## 触发条件

下列变化需要明确相应的契约与验证目标，按实际风险选择本文件的相关章节；不因此自动进入复杂求解或审批流程：

- 新增后端能力、接口、模块、协议接入、事件链路、批处理任务或跨模块调用。
- 修改 Entity / Service / Controller / Repository / Command / Event / Subscribe / Codec 等核心行为，且会影响用户可见结果、持久化数据、消息、权限、状态流转或对外 API。
- 跨边界改动改变了所有权、交互契约、时序或持久化语义。按已明确契约机械贯通多个层级时，只核对受影响路径，不额外建立设计流程。
- 需求存在多个合理方案、兼容性风险、数据迁移风险、并发或事务风险、性能风险，或用户描述仍在变化。
- 修复 bug 但需要重新定义业务语义、异常语义、边界行为或回归验证方式。

直接沿既有契约实施的场景：

- 单个字段文案、导入、注解、格式、注释或配置的小修。
- 当前请求、已接受设计或相邻契约已明确覆盖改动，只需据此补齐实现和缺少的行为证据；不要求先另写一份设计或再次确认。

## 设计与运行态落点

先遵循 [`document-placement-rules.md`](document-placement-rules.md) 区分任务契约、实时运行态和权威设计。检测到 `.trellis/` 时再读取 [`trellis-integration-rules.md`](trellis-integration-rules.md)。

1. 复用现有任务契约；需要保留待决方案时，按 document-placement-rules 选择已有宿主任务载体、Trellis 或已验证忽略的可写位置。没有安全持久载体时保留有界 active context，交接前提供便携胶囊，不自动创建目录或修改 Git 配置。
2. 实时任务拆分、步骤状态、checkbox、假设账本、失败轨迹、临时下一步和阶段总结写任务运行态；阶段切换时原位压缩，不追加历史完成清单。
3. 用户确认后，检查现有 README、docs 索引、模块文档、API 文档和 ADR。只有长期需求、稳定契约、架构 / API / 模块设计、验收语义或长期风险发生变化时，才更新其 canonical 来源。
4. 权威文档采用原位收敛：替换过时方案、删除失效描述，不追加“本轮修改”“验证摘要”“完成情况”或执行时间线。
5. 如果没有权威文档且已确认结论确有长期维护价值，才在最贴近模块的既有 `docs/design/`、`docs/adr/` 或等价目录新增文档；遵循本地命名规范，不使用 `temp`、`todo`、`note`、`summary` 这类泛名。
6. 如果任务只改变实现而不改变长期契约，允许不新增、不修改任何 docs；PR / CI 保存测试证据。

## 任务契约内容

根据本次实际变化保留足够决策的信息，已有明确内容可引用，不为未涉及的类别填空：

- 背景：当前问题、触发场景、已有实现事实。
- 目标：本次要达成的业务能力和可观察结果。
- 非目标：明确不做的范围，防止顺手扩大。
- 影响范围：模块、接口、数据结构、权限、i18n、事件、协议、缓存、定时任务、MBean / 运维操作、外部依赖。
- 方案：推荐方案、关键取舍、被拒绝方案及原因。
- 数据与边界：实体字段、查询条件、AssetsHolder 数据权限、事务边界、事件时机、消息幂等、跨模块调用方式、SQL 数据库兼容性、链路追踪与关键埋点、MBean 运维可观测性、兼容性或迁移策略。
- 稳定交付切片：只有会影响评审边界、发布顺序或独立验收的长期分解；实时执行步骤留在任务运行态。
- 测试目标：见下文，只映射本次新增 / 改变的可观察行为和真实风险，不填测试分类清单。
- 风险与待确认：需要用户确认的业务语义、数据口径、权限边界、性能或兼容性风险。

## 链路追踪与可观测性设计

新增后端能力、关键状态流转、命令执行、规则场景、协议链路、批处理、跨模块调用、事件 / 订阅或外部 I/O 时，任务契约必须说明是否需要 TraceHolder 手动埋点。

需要埋点时写清：

- 关键 span：业务阶段和稳定 span 名称。
- 关键属性：业务 ID、动作、状态、结果、数量、分支等非敏感信息。
- 上下文传播：HTTP、RSocket、消息、事件、RuleData、命令 metadata 等边界如何传递 trace context。
- 粒度控制：批量或高频链路按批次 / 阶段记录，不为每条普通数据创建噪声 span。
- 安全边界：不记录 token、密钥、完整 Authorization / Cookie、隐私字段、完整大 payload 或无界集合。

如果不需要新增埋点，任务契约写明原因，例如已有通用 filter / SQL executor / command codec / 领域 tracer 覆盖，或本次只是纯规则 / 文档 / 小范围重命名。

## MBean 与运维可观测性设计

涉及常驻内存任务、缓存、队列、buffer、重试池、死信队列、会话管理器、连接管理器、订阅管理器、协议支持管理器或后台执行器时，任务契约必须说明是否需要提供 MBean 来辅助运维定位问题。

需要 MBean 时写清：

- MBean 名称：稳定的 `org.jetlinks:type=...,name=...`，动态 name 要转义。
- 统计指标：大小、积压、死信、命中 / 未命中、输入 / 输出、成功 / 失败、丢弃数、耗时分布、最近错误、最后刷新时间等。
- 运维操作：刷新缓存、flush、compact、重置统计、手动重试、清理过期、查看有限样本等。
- 生命周期：启动注册、关闭注销，重复注册或注册失败不影响主业务。
- 安全边界：不暴露 token、密钥、完整 payload、隐私字段、无界集合；操作参数有上限，影响业务的操作要可解释、可验证。

如果不需要新增 MBean，任务契约写明原因，例如已有 `PersistenceBuffer`、`ClusterEventBus`、`LocalTracingService`、`NetworkMbeanSupport` 等同类监控覆盖，或本次能力无常驻状态。

## SQL 可移植性与性能设计

新增或改变复杂 SQL、原生 SQL、聚合、多表关联、深分页或批量写入，且查询形态、数据规模、索引、分页、并发或批量风险会变化时，任务契约只说明受影响项：

- 优先方案是否能用 `QueryHelper`、CRUD DSL、QueryParam 或当前模块封装表达。
- SQL 是否使用标准 SQL 和通用函数；除非用户明确要求或模块已限定数据库，不默认使用特定数据库方言。
- 如果必须使用数据库方言，写清数据库范围、使用原因、不可移植风险、替代方案、回退方式，并列为用户确认项。
- 性能预估：真实数据量、筛选组合、排序字段、分页深度、索引命中、并发访问、批量大小和可能的锁 / 扫表风险。
- 压力测试目标：数据规模、并发数、查询 / 写入频率、耗时阈值、资源指标和通过标准；无法压测时写明替代验证与剩余风险。

## 发布边界与兼容性判断

兼容性判断是通用发布边界规则，不只适用于 CRUD。设计时先区分“已发布事实”和“PR 内中间形态”：

- 已合入主线、已发布到生产、已有外部调用方、已有持久化数据、缓存、消息、配置、保存查询、外部链接，或已公开 API / DTO / Event / Topic / Command / 协议报文 / 前端路由参数 / QueryParam / `termType` 依赖时，才按兼容性风险处理，设计迁移、适配、灰度或过渡策略。
- 同一个 PR 内尚未发布的旧逻辑、旧字段、旧接口、旧 DTO、旧事件结构、旧 Topic、旧 Command、旧协议报文、旧配置项、旧路由参数、旧 `termType` 或旧测试期望，优先直接收敛到最终最佳实践，并同步修改同 PR 内调用方、测试和文档，不为了兼容 PR 中间形态保留多套协议、分支代码、适配器或迁移逻辑。
- 如果不确定是否已有外部依赖，先查发布记录、现有调用与用户已提供信息；仅当该事实会改变方案且仍无法判断时询问。
- PR 描述中可说明“不涉及已发布兼容性；本次为 PR 内未发布逻辑收敛”，但不要因此省略真实测试。

智能体执行约束：

- 任务契约中如果出现“兼容、旧字段、旧接口、旧参数、旧事件、旧协议、旧配置、旧路由、旧测试期望”，必须写出兼容对象来自哪里：已发布 / 已持久化 / 外部依赖 / 同 PR 中间形态 / 不确定。
- 结论为“同 PR 中间形态”时，推荐方案必须是单一 canonical 实现，并把删除旧分支、旧别名、旧适配、旧测试期望列入任务；不要给出“双写一段时间”“新旧都支持”“保留兜底解析”这类方案。
- 结论为“不确定”时，先定位可用发布或调用证据；仅当仍有实质未决选择才询问，不把猜测的兼容分支写进方案。
- 结论为“已发布 / 已持久化 / 外部依赖”时，才设计兼容、迁移、灰度、回滚或清理计划，并写清退出条件。

## 授权与未决选择

用户已明确目标、行为、范围并要求实施，或本轮明确要求按已接受方案调整时，授权持续有效；直接记录必要的契约要点并继续。新接口、跨层或协议修改本身不构成重新审批的理由。计划用于组织工作，不能制造用户尚未要求的审批流程。

仅在以下情况暂停依赖该选择的工作，并用一个聚焦问题说明具体差异：

- 多个合理语义仍会改变用户结果、权限、持久化、外部契约或验收，而当前证据和已有指令不能选择。
- 需要超出已有范围或新增权限，或用户明确要求在这一节点等待审批。
- 本地明确适用的项目审批规则要求该动作获批，且当前会话尚无相应授权。

提问前先完成已授权且不依赖该选择的工作。引用导致暂停的具体规则或未决事实，给出可审查的结果；不把沉默当授权。仅实现路径、阶段顺序或命令变化时无需重批；若实质改变已接受契约，更新该部分并按同一标准处理。

## 测试目标先行

开发前从任务契约中提取少量测试目标。下面是按变化选择的候选维度，不是必须填满的 checklist：

- 真实业务场景与数据：谁在什么状态下做什么，哪项可观察结果发生新增或变化；优先复用满足生产约束的现有 fixture、样例报文和相邻测试数据。
- 核心行为：新增能力的主路径，或 bug 的原始触发与最容易回归的已确认路径。
- 异常行为：只有本次新增 / 改变了权限拒绝、资源不存在、参数非法、状态不允许、重复请求或外部错误转换的契约时才选择。测试目标不能反向创造新的异常语义或生产 guard。
- 边界行为：只有空集合、大批量、分页、重复、并发、幂等、粘拆包或乱序等真实风险发生变化时才选择；危险删除、无界查询和资源耗尽边界必须保留 owner 级保护。
- 数据权限：只有资产类型、权限动作、关联字段、独立暴露边界或查询 / 操作控制发生变化时，按 [`../../jetlinks-assets-permission/SKILL.md`](../../jetlinks-assets-permission/SKILL.md) 验证该 owning boundary 的 allow / deny；通用 AssetsHolder 控制器已覆盖且本次未改变时不重复测试框架本身。
- SQL 性能：只有查询形态、数据规模、索引风险、分页方式或写入规模发生变化时，选择可移植性、执行计划、压力测试或最接近风险的替代验证。
- 链路追踪与 MBean：只有埋点、上下文传播、指标、运维操作或生命周期行为发生变化时才测试；仅使用了相关技术不构成新增测试目标。
- 集成验证：只有交互契约、真实装配、序列化 / 持久化语义、跨边界传播或外部系统行为发生变化，且更低层测试不能观察该风险时才触发。代码“涉及数据库、消息、事件、协议或跨模块”本身不触发。
- 验收标准：每个实际目标对应最合适 owning boundary 的检查、预期断言和通过标准；先复用仍有效证据，只补行为缺口。

新增运行时校验属于业务行为变化：它会改变可接受输入、失败时机和错误类型。DTO / schema / 框架已拥有的输入约束不在 Service、Repository 或 helper 重复；AssetsHolder、状态机或持久化事务已拥有的权限 / 不变量不在上下游复制。只有不可信输入、权威安全 / 权限、状态或持久化不变量、危险操作、已确认错误转换的唯一 owner 边界可以新增校验。禁止因“更健壮”“防御性编程”“以后可能”或“为了补异常测试”增加校验，也不要求逐条准备不加校验的证明材料。

## 开发与验证顺序

推荐顺序：

1. 复用或补充任务契约中实际改变的行为、方案与测试目标。
2. 按上文授权规则处理真正未决选择，其余已授权工作直接推进。
3. 将已接受且需要长期维护的结论原位提升到权威 docs；若长期契约未变则不改 docs。
4. 将任务契约映射到已有测试和仍有效证据；只有新增 / 改变的行为缺少证明时，才在最合适边界新增或更新测试。
5. 实现生产代码，保持改动范围与已接受契约一致。
6. 在连贯阶段结束后集中运行相关验证，不在每个操作后构建。
7. 如果实现证据表明需求、稳定契约、架构决策、验收语义或长期风险必须改变，先更新相应任务契约并按授权规则处理未决选择，再收敛权威 docs；如果只是实现假设、执行顺序或命令失败，不动权威 docs。
8. 交付前把实际使用 / 复用的验证证据、结果和真实未覆盖风险写入 PR / CI；覆盖率只按仓库门槛处理，未选择的测试类型不逐项准备“不适用”说明。权威设计不追加最终验证摘要，README 不记录测试报告。
9. 任务运行态在阶段切换时原位压缩，任务完成后由现有工作流归档 / 清理；只提升稳定结论，不复制阶段总结。

## 测试真实性约束

测试目标不是为了“让测试变绿”，而是为了证明真实业务场景可靠。

禁止：

- 删除测试、注释断言、降低有效断言、只保留 `notNull` 或空跑测试。
- 把期望值改成当前错误实现的输出，绕过真实业务语义。
- 只 mock 掉被测核心逻辑，导致测试没有验证真实分支。
- 用宽泛 `any()` / `lenient()` 掩盖关键参数、权限、状态或消息内容。
- 用随机 sleep、扩大超时、吞异常、忽略异步结果来让测试偶然通过。
- 只运行无关模块测试，或用无关覆盖率冒充本次改动覆盖率。
- 为了测试方便改变生产代码语义、放宽权限、绕过校验或新增测试专用分支。

要求：

- 断言业务结果、持久化结果、事件内容、对外响应、异常类型与 i18n code、权限行为、协议报文或消息字段中的关键事实。
- 测试数据必须能解释为什么代表真实场景；如果使用合成数据，需要满足生产约束和边界条件。
- 外部依赖不可用时，用契约测试、适配器测试、记录的真实报文或模块内已有样例替代，并明确剩余风险。
- 测试失败时先分析根因；如果根因是设计目标不合理，更新任务契约并按授权规则处理变化，不要偷偷降低测试目标。
