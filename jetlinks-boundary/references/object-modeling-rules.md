# 属性、对象与本体关系的实现选择

负责人、所属组织、设备依赖、业务关联等需求在建模时读取。先判断业务事实及其 owner，再选择存储与声明方式；不以页面字段形状决定后端模型。

## 从业务含义给出推荐

| 真实需要 | 推荐路径 |
| --- | --- |
| 设备增加保养周期、安装说明等依附值，没有独立对象身份 | 按 [版本化字段扩展](application-platform-rules.md#标准实体字段扩展) 保存属性；不为了采用本体建立无意义对象 |
| 设备关联已有用户作为负责人，只需当前关联、增删和双向查找 | 2.21 及以后且目标能力已装配时，优先复用本体的托管关系；复用原设备、用户身份，不另造人员表 |
| 负责人、空间归属或组织成员已由原业务权威维护 | 通过原 Provider / 来源暴露关系，修改仍走原业务动作；不再向通用关系表双写同一事实 |
| 任职有审批、有效期、交接记录或独立权限 / 生命周期 | 由业务 owner 承载任职 / 指派事实及必要约束，按需向本体暴露关系或独立对象；本体语义与业务存储可以组合 |
| 管理员运行时新增“设备依赖控制器”等关系，普通用户关联对象 | 动态定义托管关系，使用已有两端类型和受权范围；不为每种配置生成实体或代码分支 |
| 目标版本或部署没有所需本体能力 | 先复用已有公开关系能力；不足时由应用表保存关联并沿公开对象契约访问，不升级依赖或直接引入平台 manager |

“设备负责人”首先是设备与人的关系候选，不因 UI 是单选框就默认 `ownerId` 扩展字段。先查已有权威来源；纯关联可推荐平台托管，需要任职业务规则则推荐业务承载。既有外键可以继续作为权威存储并投影关系，不因接入本体强行迁移。

只要求“当前唯一主负责人”时，先核实关系 owner 的基数 / 原子替换能力；缺少时在正确 owner 补通用约束或复用业务写入口，不因一个唯一性要求就新建审批、任职框架。

## 定义来源与事实来源分别选择

- **代码声明**：稳定的产品语义、需随代码审查和版本交付的关系，使用 `OntologyDefinitionProvider` 贡献 `ObjectDefinition / RelationDefinition`。可声明 `provider` 或 `managed`；代码定义关系类型不等于把具体负责人写进初始化代码，声明属性元数据也不自动产生实体列或持久化。
- **动态配置**：管理员需要运行时维护关系类型、正反向名称、选择范围和启停时使用。当前 `/ontology/relations` 保存动态定义，实例固定为 `managed`，不能覆盖代码声明；不承诺通过它任意配置 Provider、建表或增加业务动作。
- **原业务维护（provider）**：事实在原字段、绑定表或业务对象中，原 `RelationObjectProvider` / `OntologyObjectSource` 提供查询，修改走原业务入口。本体声明不会自动实现查询、写入、审批或历史。
- **平台托管（managed）**：复用 relation 存储，使用正式增量入口添加 / 移除具体关联。定义来自代码也可托管；动态定义和逐条关联是两种操作，不让普通使用者反复定义关系类型。

定义与事实来源逻辑独立，但组合受当前 API 限制。相同语义保持一个权威事实来源；反向导航是同一条关系，不另建一份反向数据。不因空结果或来源故障切换事实 owner。

## 核实当前能力边界

- 用户版本策略为 2.21 及以后；仍要核验目标 BOM、制品和运行时装配。开发分支及其 `@since 2.20` 注释不能证明旧版已发布，也不能把字段扩展与对象本体当成同一能力。
- 当前托管关系维护端检查两端可见性和规范来源的资产写权限，支持增量增删与双向读取；关系存在不自动授权。业务授权继续沿 [AssetsHolder](../../jetlinks-assets-permission/SKILL.md)，组织成员或设备可见也不自动等于设备负责人。
- 当前托管实例保存端点与关系标识，不提供任意关系属性、有效期历史或单负责人唯一性保证。稳定边键只防同一条边重复，不能防一个设备关联两位不同负责人；单选 UI 和写前查重都不能替代并发不变量。
- 关联浏览的 `items / hasMore` 是候选分页契约，授权裁剪后可出现空页；不伪造可见总数。若需求是“按负责人筛设备并精确 count / 导出”，单独核实来源查询支持，不能取一页设备后过滤或全量收集远端 ID。
- 应用消费公开 core / SPI 或适用的 component 契约；管理端与存储由宿主装配。跨服务沿 [命令契约](cross-service-call-rules.md)，不为使用本体直接依赖 `ontology-manager` 或其他平台实现模块。

源码定位从 `jetlinks-ontology` 的 `RelationDefinition.InstanceSource`、`OntologyDefinitionProvider`、`OntologyCatalog`、`RepositoryOntologyRelations`、`ManagedOntologyRelations` 和 `OntologyRelationDefinitionController` 开始；已有对象发现检查 relation Provider。名称仅用于定位，实际能力以目标版本提供方、消费者和装配为准。

## 如何向用户解释

先用现有代码和需求给出一个推荐及理由，只有会改变模型而尚未明确的业务事实才追问。例如：“现有设备和用户可以直接关联，建议用平台托管关系；这个负责人是否还需要唯一主负责人约束、有效期或交接审批？”已能从上下文确定时直接推进，不让用户盲选技术名词或逐项填写问卷。

确认是稳定产品概念时优先代码声明；用户明确需要自行增加关系种类时选动态配置。界面沿原对象选择器、关联展示与原位维护表达业务语义，代码 / 动态、Provider / 托管由实现解释，不做成普通业务用户的必选配置。

## 建模依据

- W3C [Defining N-ary Relations](https://www.w3.org/TR/swbp-n-aryRelations/)（2006，Working Group Note）：当关系自身需要附加属性或涉及多个角色时，可将其建模为关系实例。用于判断任职 / 指派是否值得独立表达，不要求引入 RDF、OWL 或图数据库。
- W3C [Organization Ontology](https://www.w3.org/TR/vocab-org/)（2014，Recommendation）的 `Membership / Role / memberDuring`：区分人员、组织、角色与有时间范围的任职。可借鉴语义划分，不能据此宣称平台已有任职、有效期或标准推理能力。
