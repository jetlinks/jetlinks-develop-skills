# JetLinks 通用 CRUD 规则

本文件面向 JetLinks 系脚手架中的常规 CRUD 需求，重点是复用已有基类与分层，而不是生成大而全的样板代码。

## 适用范围

- 新增或修改 Entity
- 新增或修改 Service
- 新增或修改 Controller
- 标准增删改查
- 基础权限、校验和用户可见文案

## 第一原则：先判断当前模块的编程模型

不要机械询问用户“选响应式还是阻塞式”。

优先级如下：

1. 如果目标模块已经明显统一了风格
   - 跟随现有风格。
   - 通过控制器返回类型、服务基类、仓储接口判断。

2. 全新模块缺少参考实现时
   - 先核验已有决定、父 POM、目标依赖、服务 / 仓储基类及脚手架约定；事实足以确定时直接采用。
   - 只有这些依据仍不能选择，且不同模型会实质改变本次契约时才询问；缺少样例本身不触发提问。

## 第二原则：最小实现

1. Service 默认只保留确实需要的扩展逻辑
   - 如果基类已经提供标准 CRUD，就不要补一堆无意义方法。

2. Controller 默认只暴露用户要求的接口
   - 如果框架已通过基类或接口暴露通用 CRUD，就不要重复造轮子。

3. 查询能力优先复用已有 `_query` 或 QueryParam 体系
   - 不为每个字段单独造接口。
   - 涉及 `createQuery()`、`createUpdate()`、`createDelete()`、排序、嵌套条件、分页、QueryParam 改写、复杂 SQL 或多查询组合时，读取 `query-dsl-rules.md`。

4. 空模板仓库允许生成首个 CRUD 参考实现
   - 如果目标仓库没有可参考的 Entity / Service / Controller，不要停在“缺少样例”。
   - 允许按本规则生成最小 CRUD 骨架，作为该脚手架中的首个规范样例。

5. 校验只放在唯一拥有者边界
   - 外部 DTO、schema 或框架已完成的非空、格式、范围校验，不在 Service、Repository 和 helper 重复。
   - AssetsHolder 权限由通用 Controller、命令提供方或独立暴露边界拥有；调用方不复制提供方的权威校验。
   - 状态迁移、唯一性和持久化一致性由拥有事务 / 状态机的 Service 或 Repository 边界校验一次。
   - 空条件只有会扩大成全表删除、无界查询、大范围更新或资源耗尽时才由操作 owner 拒绝；普通空集合按既有契约自然处理。
   - 不捕获后原样包装异常；没有已确认业务语义时，不新增资源不存在、参数非法或状态不允许分支。

“更健壮”“防御性编程”“以后可能被调用”或“为了补异常测试”不构成新增 guard 的理由。当前可达路径和既有契约没有直接要求时默认不加，也不继续准备逐 guard 的证明材料。

## 校验范围与变化语义

- 先确认本次入口的输入来源、动作和不变量 owner。DTO / schema 校验格式与范围，事务 owner 保证状态与持久化不变量，独立安全边界负责其授权；同一调用链上重复执行相同查询 / 校验不能增加安全性。
- 新 guard 要保护当前可达路径上尚未保证的真实约束；能说明来源、失败后果及为何属于此 owner 即可，不要求另写证明表。没有具体缺口时不为“未来调用方”加 null / not-found / 状态预查或多层异常包装；并发不变量仍在实际变更处原子保证。
- 通用保存入口已做事务、资产绑定和校验时，命令 / Controller 复用该入口，不复制保存流程或再预检一遍。并发状态、唯一性与权限变化要求在权威操作处验证，外层预查询不能替代锁、条件更新或数据库约束。
- PATCH / 差异更新只校验已提交内容及其影响的不变量，未提交、null 清空、历史值保留分别处理。不能因为新增一个必填字段，阻止旧对象修改无关字段；完整替换、创建与状态流转按各自真实契约校验。
- 授权更新比较实际生效权限：原值不变、权限缩小和撤销不能被无关历史规则拦截；新增、扩大以及删除精确规则后激活更宽 fallback 仍需校验。仅比较提交字段是否增加不足以判断权限是否扩大。
- 不以“去重”为由删除不同主体 / 动作的独立安全检查、模型出域前授权、发布版本复核、外部返回身份核验或真实并发不变量。检查对象、时机和威胁边界不同就可能必须保留。
- 移除校验时核实可达调用方与已承诺后置条件；没有安全或状态依据的内部判空 / 异常包装直接收敛，不为删除每个 guard 新建证明文件。真实异常继续传播，必要的协议 / 领域错误转换可保留。

## 状态流转与重复请求

- 审批、支付、工单、认领、发布 / 撤销等业务动作先按已有领域契约定义合法前态、操作者和结果；不能将状态流转等同于任意字段更新，也不为普通独立字段维护额外建立状态机。
- 读到状态后再写回并不能仲裁并发。按真实不变量选择既有锁、revision / CAS、条件更新、唯一约束或幂等机制，并检查影响行数；`@Transactional` 是否经过实际代理 / 事务操作符、是否覆盖全部写入也要核实，不能只看注解存在。
- 需要重复提交 / Worker 重放保护的动作复用已有请求身份和回执。幂等键须能区分对象、动作与相关版本；同键不同主体 / 载荷不能直接当成功，不同合法请求也不能因时间窗口相近而被误去重。
- 回执、业务状态和必须一致的投影 / 本地待办按真实事务边界提交；历史保留和外部调用分别由 [运行留痕](../../jetlinks-conventions/references/runtime-state-rules.md#历史审计与可观测性) 与 [调用恢复](../../jetlinks-boundary/references/cross-service-call-rules.md#结果失败与恢复) 约束。超时不代表未执行，不能单纯重跑整个业务动作。
- 终态、取消、转交、定义升级和迟到完成按目标版本与状态仲裁，防止旧任务覆盖新结果。复用现有状态 / 生命周期 owner，不为每个 CRUD 新造锁表、回执表或工作流引擎。

## 推荐工作流

1. 找一个目标模块内最像的 Entity / Service / Controller
2. 复制结构和注解组合
3. 只替换业务字段、路径、权限 ID、文案
4. 如果用户确实要求自定义逻辑，再补服务或控制器方法

如果当前仓库缺少参考实现，改用以下回退顺序：

1. 根 `pom.xml` 与依赖决定技术栈边界
2. 现有少量注解、导入和目录结构决定包路径风格
3. 本规则决定最小 CRUD 骨架
4. 只有关键决策无法判断时才询问用户

## Entity 规则

受资产数据权限控制的实体先满足 [资产实体契约](../../jetlinks-assets-permission/references/assets-holder-rules.md#资产实体契约)，再选择本模块基类与字段；不要只给 Controller 配权限而遗漏实体声明与继承。

扩展平台标准实体字段时按 [字段扩展版本边界](../../jetlinks-boundary/references/application-platform-rules.md#标准实体字段扩展)：2.21 及以后核验声明式能力和主对象启用，旧版用业务中间表；不直接修改、复制或继承平台实现实体承载应用字段。

优先确认：

- 使用哪种基类或接口承载 ID、扩展字段、审计字段
- 是否普遍启用实体事件
- 字段是否需要 JSON、枚举、默认值、只读、校验分组
- 表名和字段长度是否跟随相邻实体

常见做法：

- 通过基类或接口承载通用字段
- 用 `@Schema` 或等价注解描述对外字段
- 用专门注解处理 JSON、枚举、默认值
- 仅在当前模块已有此惯例时补齐创建人、修改人等字段

当没有相邻实体可参考时：

- 生成最小实体，不额外塞入与需求无关字段
- 优先使用最通用的 ID、名称、描述、创建修改时间等模式，但仅限用户需要
- 需要审计字段时，优先选择当前依赖体系已经支持的接口或基类

## Service 规则

优先复用：

- 通用 CRUD 基类
- 树形实体服务基类
- 资产实体服务基类

只在以下已由业务契约确认的情况增加逻辑：

- Service / 事务真正拥有的保存前不变量校验
- 保存后同步
- 批量更新或批量删除
- 聚合查询
- 调用其他边界能力

## Controller 规则

优先复用：

- 通用 CRUD 控制器接口或基类
- 资产控制器基类
- 树形控制器基类

补充自定义接口的前提：

- 用户明确要求
- 通用 `_query` 无法表达
- 该模块已有同类定制接口模式

当没有相邻控制器可参考时：

- 先生成最小 CRUD 控制器骨架
- 只保留资源路径、权限标识和服务绑定
- 自定义查询、批量操作、联动接口默认不生成

## 权限与文案

1. Controller 上的资源权限 ID 复用模块现有命名方式
2. 自定义动作只有在现有模块使用 `@ResourceAction` 或同类注解时才新增
3. 涉及 CRUD 查询、详情、更新、删除、批量操作、导出或自定义接口时，必须分析是否需要 AssetsHolder 数据权限控制
   - 具体实现切换到 [`../../jetlinks-assets-permission/SKILL.md`](../../jetlinks-assets-permission/SKILL.md)
   - 优先复用 `@AssetsController`、`AssetsHolderCrudController`、`CorrelatesAssetsHolderCrudController`、`AssetsHolder.injectQueryParam`、`AssetsHolder.assertPermission`、`CrudAssetPermission`
   - 不要手写租户、机构、部门、创建人过滤来替代 AssetsHolder
   - 先查目标版本与相邻契约；只有仍未确定且会改变访问范围的资产归属、动作或例外语义才询问，不能自行全放行或全拒绝。
4. i18n 是否补齐，以当前模块约定为准
   - 若模块已有 i18n 资源并对权限、动作、字段做本地化，则补齐
   - 若模块尚未建立这套约定，不要臆造单独规则
5. 已确认契约要求的保存前校验、唯一性冲突、资源不存在等用户可见异常，优先沿用当前模块的 `i18nCode` / message key 异常写法
   - 不要直接 `throw new XxxException("名称已存在")`
   - 若本地异常模型只支持 `message`，再在边界层回退到本地化后的 message

## 注释落地

- 新增或修改对外 Entity、DTO、Controller、Service、Command、Event 时，按公共契约补类注释；标准继承型 CRUD 若完全无自定义语义，可沿用相邻模块简化。
- 自定义接口、复杂校验、AssetsHolder 权限边界、兼容旧查询 / 参数、批量上限、复杂 QueryHelper / SQL / DSL 组合，需要在代码旁边写 1 到 3 行短注释说明业务原因或边界。
- 不给简单字段、getter / setter、直接 DTO 搬运、标准基类委托写噪声注释。

### 低上下文模板仓库下的权限默认规则

如果当前仓库没有可参考的权限命名：

- 资源权限 ID 使用稳定的 `kebab-case`
- 优先由“领域名 + 资源名”组成
- Controller 路径、权限 ID、资源名称保持一一对应
- 只有存在真正的自定义动作时才新增 action 级权限
- 不要在首个 CRUD 骨架中一次性定义过多细粒度权限

## 何时跳到高级规则

遇到以下情况时，继续读取 `advanced-crud-rules.md`：

- 动态复杂查询
- 关联查询
- 批量处理
- 复杂 SQL、原生 SQL 或 QueryHelper
- 性能敏感分页
- CRUD 后强副作用联动

遇到以下情况时，继续读取 `query-dsl-rules.md`：

- `createQuery()` / `QueryParamEntity` DSL 查询
- `createUpdate()` / `createDelete()` 批量更新或删除
- 默认排序、多字段排序、分页稳定排序
- `nest` / `orNest` / `toNestQuery` 嵌套条件
- `setParam` 合并前端筛选与服务端固定条件
- AssetsHolder 查询注入前后的 DSL 组织
- `QueryHelper.transformPageResult` / `combineOneToMany` 多查询结果组合

## 自检清单

- 是否沿用了目标模块的编程模型
- 是否复用了现有 CRUD 基类或接口
- 是否只生成了用户需要的代码
- 是否避免了重复查询接口和重复样板
- 是否只在 owning boundary 校验一次，并删除了框架 / 上游已经保证的重复 guard
- 权限、路径、文案是否与当前模块一致
- 是否分析了 AssetsHolder 数据权限：资产类型、权限动作、查询注入、详情访问、更新删除校验、批量操作和关联资产边界
- 是否为公共类、自定义接口、复杂校验、权限边界、兼容逻辑、批量上限或复杂查询补了必要代码注释
- 若处于空模板仓库，是否明确区分了“来自现有工作区的事实”和“来自通用规则的默认决策”
