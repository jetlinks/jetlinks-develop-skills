# JetLinks 实时订阅规则

本文件用于处理 Topic、消息流和实时事件消费。

## 何时使用

- 当前需求是持续消费而不是一次性请求
- 需要 `@Subscribe`、EventBus、消息总线或系统 Topic
- 需要处理设备消息、广播消息、系统事件流

## 核心原则

1. Topic 必须来源于当前工作区的真实约定
   - 先查现有订阅者、常量、Topic 工具类、事件定义。

2. 订阅处理器要保持幂等
   - 消息重放、重复投递、共享消费在实时场景里很常见。

3. 高吞吐场景要考虑缓冲与批量
   - 如果当前模块已有 `buffer`、`window`、批处理 sink、去重策略，优先复用。

4. 不把一次性查询伪装成订阅
   - 订阅是流式消费，不是远程查询替代品。

## 设计顺序

1. 确认消息来源
   - 设备消息、系统消息、领域广播、业务广播。

2. 确认 Topic 形状
   - 核对来源定义和统一 Topic 构造器；相邻样例只提供线索，不复制其维度、权限范围或业务标识。

3. 确认订阅特性
   - 本地、broker、shared、优先级、缓冲策略等，以现有模块约定为准。

4. 确认输出动作
   - 持久化、转发、聚合、同步缓存、触发事件。

## 推荐做法

- 返回 `Mono<Void>` 或当前框架惯用的异步类型
- 在处理器内部保持非阻塞链路
- 高频消息按身份和交付语义选择批量、合并或降噪；频率高不代表重复，不默认丢弃事件
- 把复杂业务拆到服务层，不把整个流程都塞进订阅方法

## 连续流的语义与生命周期

- 一次性历史查询与持续实时流可以在一个用例中组合，但明确二者交接、ready / 完成信号、空历史、快照与迟到值；不能先查历史再订阅造成交接空洞，也不能默认重复订阅副作用源。具体方案按已有 source 契约选择。
- 按消息语义控制背压：最新状态可按业务键保留最新，事件 / 告警 / 历史 / 交易必须按交付契约处理，不能通用 DROP_OLDEST、随意采样或仅按时间窗去重。重放身份和乱序规则来自来源，溢出 / 断线应有明确结果和恢复边界。
- 查询、推送和订阅复用统一维度 / 资产与 Topic 构造契约；能按授权范围订阅就不每条消息重新查所有用户 / 维度。不要手拼相冲突的 Topic 命名空间或默认用原始全量 Topic 作无权限回退。
- 订阅采用哪个认证快照、何时响应权限变化由既有入口 / 同步 owner 负责；Provider 不各自注册一套权限刷新，长期订阅也不能忽略平台要求的撤权机制。非 HTTP 的授权与 trace Context 沿来源传递。
- 取消、断线、重连、切换对象、停用及关闭时释放本消费者的监听、去重 / 缓冲状态与定时器；重连按约定恢复位置，不能静默丢历史，也不能自动重做有副作用命令。共享连接不被单个消费者关闭。

## 注释落地

- Topic 兼容、共享订阅语义、消息重放幂等、去重窗口、buffer / window 边界、失败重试、订阅释放或上下文传播如果不是显而易见，必须在订阅处理器或 helper 方法旁边写短注释。
- 注释说明业务边界、协议 / Topic 来源、重放或批量策略；不要逐行解释 Reactor 操作符。
- 只做简单转发且方法名已经说明语义时，可不写实现注释。

## 自检清单

- Topic 是否来自真实代码或常量
- 订阅特性是否与现有模块一致
- 处理器是否幂等
- 是否避免了阻塞和逐条低效操作
- 是否为 Topic 兼容、重放幂等、批量 / 去重边界或订阅生命周期补了必要代码注释
