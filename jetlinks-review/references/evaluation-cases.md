# 正反场景

维护本技能及规则 owner 时，用以下场景检查理解边界。它们是可复用的评估输入与预期，不是已执行的智能体评测结果；结构 / 链接校验不能证明行为通过。不要求普通业务任务逐项演练。

告警、计算、通知的复用与过度复用对照统一维护于 [平台能力场景](../../jetlinks-boundary/references/platform-capability-reuse-rules.md#场景对照)，不另复制一套能力清单。

| 场景输入 | 预期判断 |
| --- | --- |
| 应用与平台同进程，直接依赖 device-manager 并注入内部 Service | 违反平台边界；沿公开契约 / 命令修复，不能用同部署或 optional scope 免责 |
| 平台启动聚合模块装配 authentication-manager | 正常宿主职责；不能只按依赖名报告违规 |
| 应用 core 引用上层 manager DTO，公共算法使用 UI 的坐标类型 | 确认导入方向与 owner；将稳定语义归正确契约层，不只移动文件 |
| 2.20 应用为设备增加维保字段 | 自有中间表与公开主对象契约，不依赖 DeviceEntity 或假设开发注解已发布 |
| 2.21 BOM 中没有声明式扩展，开发分支 @since 却写 2.20 | 核验实际能力，按项目版本策略采用表关联方案；不能凭注释声称旧版可用 |
| 2.21 已启用主实体，一对一依附属性；另一需求有独立权限和多次历史 | 前者声明式扩展；后者独立业务对象 / 关系，不能统一塞 customFields |
| 有 relation，未装 ontology；设备只需当前负责人关联与反向查找 | 先查事实 owner，无已有来源时复用 relation 托管能力；不要求安装 ontology、不默认新增 ownerId 或中间表 |
| 业务只依赖 ontology-core 并实现 OntologyDefinitionProvider；另一模块是本体内部 relation 适配器 | 前者仍违反业务声明边界，改用 relation / core；后者按本体消费者职责判断，不能按类名一律禁止 |
| 为原设备补摘要 / 动作而注册第二个 device Provider；既有外键加 PropertyReference | 前者沿 ObjectSupportProvider / 注解补充能力；后者只补引用语义，不假设自动建关系、持久化或授权 |
| 固定关系类型由代码交付，管理员另需动态配置；设置 managed 后只验证一个写入口 | 使用 relation 契约并分别核验定义和事实 owner；标记不证明全部导航 / 查询支持，不借 ontology SPI 补缺口 |
| 负责人要求唯一主责、任职有效期与审批；托管边键已去重 | 由业务 owner 承载不变量与任职事实，经 relation 暴露；不同负责人是不同边，去重或 UI 单选不证明唯一与历史能力 |
| relation 返回 PagerResult，本体关联浏览返回 items / hasMore；设备按负责人筛选要求精确 count | 分别核验分页契约与来源查询，不套用候选页语义、不伪造总数或先分页后过滤，关系不自动授予权限 |
| DTO、Controller、事务 Service 对同字段同动作重复查库预检 | 核对唯一 owner，删除重复流程；事务内真实不变量和数据库约束保留 |
| HTTP 与 RPC 接收相同主体 / 资产 / 动作，只有 HTTP 路径经过授权 | RPC 仍须经适用的授权 owner；若两入口均实际委托完整授权的命令提供方，则不再复制检查 |
| 负责人和维护人两种关系各新建 termType，已有 relation-member 接收 relationId | 按现有结构化值契约复用；仅目标制品支持的同库单跳可用，不推广为跨服务 SQL 关系查询 |
| 给 I18nSupportException 的 code 后追加默认文案，再传 {0} 对应的对象 ID | 核对构造器；文案会成为第一个格式化参数，保留 code / 真实 args，不自造 fallback 参数 |
| 内部已校验字段再判空，同时另有模型出域权限和返回身份校验 | 只移除无依据重复 guard，保留不同威胁边界的必要检查 |
| 旧对象新增必填字段后仅 PATCH 名称，却要求补齐全部字段 | 核对差异更新语义；不让新必填约束误拦无关更新，仍保证受影响不变量 |
| 撤销角色菜单时无关旧权限未变；另一操作删除精确规则激活通配规则 | 前者不应重新索取全部历史授权；后者可能扩大实际权限，必须核验 |
| 同事务 Mono.zip 两个 DB 查询，或 flatMapSequential 多个写入 | 输出顺序不保证串行执行；批量 / 串行并核对连接与游标，不新开事务绕过 |
| concatMap 在未消费完的 DB 游标内逐条再查同连接 | 不能仅因用了 concatMap 就放行，检查重叠语句与批量替代 |
| 事务外少量独立远程读取用 zip；纯内存流使用默认 flatMap | 无共享事务资源等真实风险时允许，不强制全部串行或显式并发参数 |
| 每请求把并发开到连接池上限，存在多请求和嵌套 fan-out | 核对全局负载和池预算；优先批量，不能复制固定数值或只凭代码宣称压测通过 |
| 纯转换方法返回 Mono；另有 defer 负责每次订阅读取 Context | 转换保留普通函数；真实订阅期边界保留，不能把两者都删成即时求值 |
| 业务表新增 tenantId 并手写过滤；权限 Provider 实现维度；工单关联客户 | 首项违反统一契约；后两项按职责判断，不能仅凭字段名删除 |
| 通用启动器创建某客户设备 / 模板；业务安装显式导入模板；平台注册能力元数据 | 首项移回业务安装 / 选装，后两项可合理；保留幂等与用户修改语义 |
| 为旧检索题加关键词权重；统一预算中同一个倍率写了三处 | 修共同策略及重复 owner；常量重命名不等于消除特调，不继续逐题调参 |
| find 无匹配返回 empty，必选 RPC 缺少命令也 empty，业务 Mono<Void> 正常完成 | 仅必选执行缺失按契约报错；不全局改写合法空结果，不额外预检再执行 |
| 有长文件、数字 0/1 和一层简单转发，但没有行为 / 职责证据 | 信号不足以报告缺陷；检查转发是否有真实公共边界，不凑问题数量 |
| 接口返回不带分页元信息的列表，调用方因此认为没有分页 | 分别核验返回形状与 paging 契约，不能默认全量，也不自行改变平台分页规则 |
| 一对多展开后分页或统计，同一父对象出现多行 | 按业务粒度、去重、权限和 count 追完整查询，不因用了标准 DSL 就认定语义正确 |
| 审批先读 revision 再无条件写，重复请求复用同键但载荷不同 | 核实真正 CAS / 锁和幂等载荷契约；旧前态检查和同键命中不能替代并发仲裁 |
| 命令已被远端执行但响应超时，客户端换节点重试 | 结果未知不等于未执行；按已有幂等与回执恢复，不凭重试成功断言没有重复副作用 |
| 导入前半批已写入，失败后 fallbackSingle 重跑整批 | 检查原子性 / 幂等，不把框架提供 fallback 当安全证明；区分整批与逐项结果 |
| 删除操作的本地关联清理被移到提交后；普通通知也被强制新增 outbox | 前者检查本地不变量，后者确认真实可靠性需求；不将所有副作用统一异步或可靠化 |
| 投递返回 accepted，UI 显示业务已执行完成 | 沿消费者确认回执阶段；持久受理、执行完成和最终结果不能混用 |
| 历史查询完成后才订阅增量；另一个流为可合并的最新状态 | 核验交接是否有补读保障；前者可能漏数据，后者可按键合并，不能统一套丢弃策略 |
| 五秒去重丢掉两个不同告警；合法重复事件携带同一消息 ID | 幂等使用真实事件身份；不同合法事件不因时间近而被吞，重复投递按 owner 收敛 |
| 配置保存后引擎启动失败，旧实例仍回写；点位每条数据重新编译 | 检查定义与运行版本、热路径和资源替换；不以数据库保存成功证明已生效 |
| 缓存只有 TTL、无容量限制，key 缺少 scope；另一缓存是平台权威事实的正式入口 | 前者追规模与串值，后者优先正式契约；不要为消除所有查库另建平行缓存 |
| 普通读取增加全量审计快照，另有必须同事务保存的流程历史 | 前者核实真实用途和重复留痕，后者保留必要证据；不能统一禁历史或以 trace 代替回执 |
| 列表为未开启的统计展示 0，并逐行查大历史 | 同时检查用户用途、缺失语义和查询成本；界面更饱满不能证明内容应存在 |
| DTO 经 JSON 互转后大整数失真、日期丢时区、未提交变默认值 | 沿全链类型和提交契约检查；不能仅以序列化成功或 schema 存在为验收 |
| 用户切换对象后旧保存完成，清除新对象 loading；卸载时 debounce 仍待执行 | 请求 / generation 与资源生命周期一并核验，不能只检查 onUnmounted 调用了 unsubscribe |
| 历史评审要求某旧 helper，当前版本已有统一替代；问句未证实故障 | 核验当前契约和合理反例，保留通用意图，不复制旧 API、旧路径或未证实结论 |

## 防过度与组件缺陷的对照

| 场景输入 | 预期判断 |
| --- | --- |
| 新增受资产权限控制的实体只配置 AssetsHolderCrudController，无有效 @Asset 元数据且未继承 ExtendableEntity | 补正确资产类型 / ID 映射及 ExtendableEntity 继承契约，不能只检查端点；不新增租户字段代替 |
| 受控实体已通过平台基类继承 ExtendableEntity 且有效资产元数据正确；旁边有只携带资产 ID 的 DTO | 复用既有继承与元数据，不造重复实体层，也不强迫 DTO 继承持久化实体 |
| 多处复制同一权限组合 / 字段语义，目标解析器支持组合注解 | 在所属能力统一定义并复用，核对有效资源、动作、组合逻辑与元数据；不逐处复制，也不取消独立入口授权 |
| 将方法权限搬到接口后仅凭 @Inherited 删原注解；另有两个相似注解实际动作不同 | 核验真实层级解析与覆盖后再收敛，保留权限差异；不能以减少重复为由扩大授权或丢失语义 |
| 多处同义编解码复制，拟放通用工具；另将数据库写入、授权与投递塞入静态 Utils | 前者先复用或补所属工具并保留数据语义，后者留对应服务 / 组件；不把所有重复都工具化或增加无职责转发层 |
| 实体已有 @Asset 与 ExtendableEntity，自定义端点 ignore=true 却无等价权限处理 | 实体声明不能替代入口授权，仍在正确 owner 补 AssetsHolder 控制 |
| 单次数据映射引入插件注册器和多层策略，理由仅为未来可能复用 | 删除无当前消费者 / 契约的机制，保留直观转换，不为消除特判再造框架 |
| 只有一个消费者，但封装明确资源生命周期或稳定公共 SPI | 允许合理抽象，不能按调用次数判定过度设计 |
| 已有 DTO 约束，内部 helper 再判空；另有外部回调签名与事务 CAS | 移除无依据重复 guard，保留独立信任边界和并发不变量 |
| 为减少方法数把权限、查询、状态更新与投递塞进嵌套链；另一改动将每行拆成 helper | 两者按实际理解成本收敛，命名完整业务阶段，不按方法 / 操作符数评分 |
| 超时常量名清楚但没有单位与依据；数组索引 0 和正常条件分派 | 前者核实策略 owner，后者可保留，不把所有数字和 switch 视为魔法值 |
| 通用选择器丢失回显，业务用私有复制或深层 CSS 修补 | 在选择器 owner 修复并提交 PR，验证原始触发和受影响同类，调用方接正式修复 |
| 组件正确，业务通过公开 slot 表达领域选项 | 合理配置 / 扩展，不误判为规避；不要求无缺陷组件另开修复 PR |
| 通用修复仓库不可写或尚未发布 | 保留可审查补丁、接入关系与具体阻塞，不以业务绕过宣称完成 |

## 任务整体审查的对照

| 场景输入 | 预期判断 |
| --- | --- |
| 任务三个提交依次改变模型、命令与 UI，最后还有未提交修复和新文件 | 按真实任务基线审累计结果及相关工作树，追命令消费者和 UI；不能只审最后提交或分项测试 |
| 数百文件按已确认契约机械改名；另一任务仅改几行公共权限默认值 | 前者采用相称范围，不增全套审查；后者追受影响入口及未改消费者，核对合法允许和真实拒绝 |
| 通用组件上游 PR 已修复，但业务仍锁旧版；数据库保存成功但运行实例未替换 | 分别核对接入版本和实际生效路径，不把 owner 修复或保存成功当整个任务完成 |
| 中途已有有效链路证据，最终只修另一局部路径；进入 PR 阶段且 commit hash 改变 | 复用未受影响证据，只补修复影响的审查与验证；不因交付阶段或 hash 变化重跑全部检查 |
| 用户要求整体审查，只提供本仓；另仓消费者不可获取，发现无关旧代码缺陷 | 明确消费者未核实的限制，区分存量问题；不宣称全局通过，不擅自修复、提交或扫描全部历史代码 |

验收关注是否选择正确 owner、保留真实反例、给出可定位证据、避免未授权修改与多余验证。若要声称智能体行为优于旧规则，需在相同源码、工具和任务下执行实际对照，记录误报、漏报及成本；不以关键词命中率替代。
