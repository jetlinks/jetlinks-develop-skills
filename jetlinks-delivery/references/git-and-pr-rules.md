# Git、分支、PR 与测试交付规则

当任务不仅涉及“写代码”，还涉及“提交代码、准备交付、发起 PR、说明测试结果”时，读取本文件。

如果任务重点是中文 commit message 起草、合规审查或 shell 提交命令，继续读取：

- [`commit-message-zh.md`](commit-message-zh.md)
- [`shell-commit-examples.md`](shell-commit-examples.md)

## 目标

确保 JetLinks 项目的交付过程符合以下要求：

- 提交标题对齐仓库既有风格
- 禁止直接 push 到主干或集成版本分支
- 通过 PR 合并
- 后端新增功能或既有功能变动必须在拥有该变化的边界具备有效行为证据；已有证据有效时直接复用
- 较大后端改动或新功能必须先有已确认的任务契约和测试目标；权威文档只同步长期稳定结论
- 提交与交付前确保变化行为已有仍有效的最合适验证证据；只有跨边界契约或真实装配语义变化时才要求集成证据
- 交付前确认必要文档已与实现保持一致
- 复杂 SQL 或原生 SQL 的方言发生变化时说明数据库兼容性；查询形态、规模、索引、分页、并发或批量风险变化时才要求真实性能验证
- 复杂逻辑、公共类和 SPI 扩展点需要说明注释 / 公共契约结论
- 关键后端业务链路需要说明 TraceHolder 链路追踪埋点决策
- 常驻内存任务、缓存、队列或后台执行器需要说明 MBean 运维可观测性决策
- 在 PR 描述中用可核验结果说明验证；覆盖率仅在仓库有门槛或已有可靠数据时作为门禁 / 诊断信息

## 提交标题规范

优先对齐仓库现有历史，默认采用：

```text
type(scope): summary
```

约束：

- `type` 与仓库历史保持一致，优先使用 `feat`、`fix`、`refactor`、`docs`、`test`。
- `scope` 选择本次改动的真实模块、业务域或规则域。
- `summary` 使用简洁中文动宾短语，直接说明结果。
- 除非历史明确允许，否则不要省略 `scope`。

参考仓库历史风格：

- `refactor(prompt): 扩展低上下文边界决策规则`
- `refactor(基础模块): 优化菜单逻辑`
- `refactor(设备管理): 优化实体拓展型`

避免：

- `update`
- `fix bug`
- `misc`
- `test`
- 无法体现模块和结果的空泛标题

如需进一步决定 `type`、`scope`、`body`、`footer` 或 ready-to-run 命令形式，转到
[`commit-message-zh.md`](commit-message-zh.md) 和
[`shell-commit-examples.md`](shell-commit-examples.md)。

## 分支与合并策略

禁止直接 push 到以下分支：

- `master`
- `main`
- 版本集成分支，例如 `2.11`、`2.12`
- 其他被团队视为主线或发布线的长期分支

标准流程：

1. 确认目标合入分支，例如 `2.12`。
2. 从该基线分支拉出临时开发分支。
3. 将任务划分为少量有独立验收信号的连贯阶段；每个阶段完成并集中验证后，在用户允许提交时创建一个本地 commit，再用实际 commit hash 和下一步刷新 Recovery Capsule、Continuity Metadata 与 Source Snapshot。用户禁止提交时保持 `Checkpoint.In-flight(validation=passed)` 并记录证据，不伪造 checkpoint。
4. 阶段内部不按命令、文件、步骤或单个小修频繁提交；未完成总体验收前不 push。
5. 所有阶段和总体验收矩阵完成后，统一 push 临时分支到远端。
6. 创建或更新一次 PR，base 指向目标版本分支，并用最终事实重写 PR 描述。

## 阶段提交与远程交付事务

阶段边界必须同时满足：

- 该阶段对应一个清晰的不变量、契约切片或可独立评审的能力，不是“改了一个文件”。
- 生产代码、调用方、测试和必要的权威文档同步已形成最小完整闭环。
- 该阶段的聚焦验证已通过，或阻塞已明确且用户接受将其作为独立提交。
- 阶段要进入 `Checkpoint.Validated` 前必须已有可引用的本地 commit；提交前的暂停状态只能记为 `Checkpoint.In-flight`。

阶段事务固定为：完成最小闭环 → 集中验证 → 若结果改变路线先刷新陈旧运行态 → 在用户允许时创建一个本地 commit → 用实际 commit hash、最新 HEAD 和唯一下一步刷新 [`../../jetlinks-router/references/context-recovery-rules.md`](../../jetlinks-router/references/context-recovery-rules.md) 的 Recovery Capsule、Continuity Metadata 与 Source Snapshot。三个逻辑视图必须位于不受 Git 管理的 runtime / checkpoint，避免更新 hash 后再次弄脏工作树或形成元数据提交循环。commit 表达该阶段的结果；不要因单个命令成功、一个测试变绿、一处 import 修正或一个文件编辑就提交。

远程操作是整个任务的单一交付事务：

- 所有阶段完成、总体验收矩阵通过、权威文档同步与发布边界检查完成后，才 push 当前分支并创建或更新 PR。
- PR body 只保留当前最终可审查事实；原位更新过时内容，不追加“Phase 1 完成”“本轮修复”“今日进展”等流水。
- 不用 PR 评论、反复 force-push、重复开关 draft / ready 或多个同任务 PR 记录每一步。
- 用户明确要求共享中间分支、外部 CI 必须依赖远端、或明确要求提前开 draft 时可以例外；执行前说明目的、未完成边界和后续仍只维护同一个 PR，不创建逐步 PR。

如果用户要求“直接推到 2.12”这类操作，应改为：

- 说明该分支属于受保护主线，不直接 push。
- 改走“临时分支 + PR”流程。

## GitHub PR 创建方式

如果当前仓库远端是 GitHub，且用户要求“发 PR”“提交 PR”“推到 GitHub 并开 PR”，默认推荐使用 `gh` 创建 PR，而不是只给一个网页链接让用户手动补完。

推荐顺序：

1. 用 `gh auth status` 检查 GitHub CLI 是否已登录。
2. 用 `gh repo view` 确认仓库、默认分支和目标 base。
3. 确认所有阶段已本地提交且总体验收矩阵完成。
4. 在创建 PR 之前，先确认用户是否认为当前任务已经完成。
5. 如果任务未完成，默认继续本地开发，不主动 push 或创建 PR；仅当用户明确要求提前共享时创建一个 draft PR。
6. 如果任务已完成，且用户确认可以进入评审阶段，统一 push 后创建 ready for review 的 PR。
7. 在临时分支 push 完成后，优先使用 `gh pr create` 创建 PR。

带沙箱的 agent 环境额外约束：

- 如果当前工具支持非沙箱审批或提权机制，`gh` 相关命令不要在沙箱内执行。
- 包括 `gh auth status`、`gh repo view`、`gh pr create` 在内，都应通过当前工具支持的非沙箱机制执行。
- 如果当前工具不支持非沙箱执行，直接说明环境限制，再按可用权限尝试或降级为提供可点击 PR 链接。
- 如果认证失效，先明确阻塞点，让用户完成 `gh auth login` 后再继续。

状态选择约束：

- 不要替用户假定“已经完成，可以直接 review”。
- 只有用户明确确认已完成，或上下文中已清楚表明“请直接提评审 PR”，才创建 ready for review。
- 如果上下文不明确，默认先问；确认未完成时默认不创建 PR，除非用户要求 draft。

允许的降级方式：

- 如果 `gh` 未安装，先说明阻塞原因。
- 如果用户不希望 agent 直接创建 PR，再退回到提供可点击的 PR 链接。
- 只有在 `gh` 不可用或用户明确要求手动处理时，才不使用 `gh pr create`。

## 任务与 PR 边界

一个已确认任务对应一个远程 PR。若需求包含多个可独立交付、独立验收的主题，应在开始实现前拆成多个任务；每个任务仍各自遵守“阶段本地提交、任务完成后单一 PR”，不能在一个任务执行中按阶段临时开多个 PR。

推荐做法：

1. 一个任务 / PR 只解决一个清晰的问题或一组强相关改动。
2. 如果需求同时包含互不依赖的功能、重构、修复或文档主题，先拆任务和验收标准，再分别进入实现。
3. 如果工作树里存在明显无关文件，不要一次性全部提交。
4. 如果确实无法拆分，也要在 PR 描述中明确说明为什么必须合并提交。

不推荐：

- “顺手一起改掉”的跨主题提交
- 未先拆任务就形成超大 diff 且缺乏清晰边界的 PR
- 把用户尚未确认完成的多个阶段性成果一次性塞进 review PR
- 每完成一个步骤就 push、创建新 PR、改 PR 状态或追加进度评论

## PR 内未发布变更的兼容性

兼容性判断不只适用于 CRUD。同一个 PR 内调整尚未合入主线或发布生产的逻辑时，优先把 PR 收敛成最终最佳实现，而不是为了兼容中间提交保留额外代码。

优先收敛的场景：

- 旧字段、旧接口、旧 DTO、旧事件结构、旧 Topic、旧 Command、旧协议报文、旧配置项、旧前端路由参数、旧 QueryParam、旧 `termType` 或旧测试期望只存在于当前 PR 的早期实现。
- 调用方也在同一个 PR 中，可以同步修改。
- 没有已保存查询、持久化数据、外部系统、生产配置或已发布 API 依赖旧形态。

需要保留兼容或迁移的场景：

- 旧逻辑已经合入主线、发布生产或被其他分支 / 外部调用方使用。
- 已有数据库数据、缓存、消息、配置、保存查询、Topic、Command、API 契约、协议报文、前端外部链接或用户已保存状态依赖旧形态。
- 用户明确要求兼容历史行为。

交付要求：

- 交付前主动搜索本次改动中的兼容、fallback、deprecated、legacy、旧字段、旧接口、旧参数、旧事件、旧配置等痕迹；凡是没有已发布、持久化或外部依赖依据的兼容代码，都必须在进入 ready for review 前删除。
- 如果是 PR 内未发布逻辑收敛，PR 描述中说明“不涉及已发布兼容性”即可，不要新增无意义兼容分支。
- 如果需要兼容，写清兼容对象、退出条件、迁移方式和后续清理计划。

## 后端设计与测试驱动门禁

较大的后端改动或新功能进入交付前，必须确认已执行设计与测试驱动流程。触发条件和任务契约要求以
[`../../jetlinks-router/references/backend-design-test-driven-rules.md`](../../jetlinks-router/references/backend-design-test-driven-rules.md)
为准。

交付前必须核对：

- 任务契约已写入 Trellis active task，或经 Git 忽略验证的单一本地运行态文件，而不是只停留在对话或误写进权威 docs。
- 任务契约包含目标、非目标、影响范围、方案取舍、稳定交付切片、测试目标、风险和待确认项；实时步骤、失败轨迹和阶段总结留在运行态。
- 用户已明确确认任务契约；已接受且长期需要维护的结论已原位同步到权威来源，删除过时描述，没有追加任务总结或完成流水。
- 测试目标先于实现制定，映射真实使用场景和数据；主路径、异常、边界、权限、性能和集成属于按本次行为 / 风险变化选择的候选，不是必填清单。
- 涉及 CRUD 时，已按 `$jetlinks-assets-permission` 分析 AssetsHolder 数据权限控制：资产类型、权限动作、查询注入、详情访问、更新 / 删除 / 批量操作校验、关联资产边界；拿不准的资产类型、关联字段、权限动作或例外规则已询问用户。
- 涉及复杂 SQL、原生 SQL、聚合、多表关联、深分页或批量写入时，已确认优先使用 QueryHelper / CRUD DSL / 标准 SQL；如使用特定数据库方言，已在任务契约及对应权威技术文档（需要长期维护时）写明用户要求、数据库范围、不可移植风险和替代方案。
- 查询形态、数据规模、索引、分页、并发或批量风险发生变化时，SQL 性能目标只覆盖受影响维度；需要压测时已有明确阈值，否则选择能直接观察风险的执行计划或定向验证。
- 涉及复杂业务、公共类、SPI / 扩展点、Provider、Codec、Listener 或 CommandHandler 时，已确认注释边界：类注释和 SPI 方法注释完整，必要 `@since` / `@see` 已指向真实版本、订阅相关类型、默认实现或参考实现，普通实现注释保持简洁。
- 已检查本次 touched backend files：必须注释的业务分支、权限边界、兼容逻辑、生命周期保护、TraceHolder / MBean 决策、协议 wire 规则、事件订阅幂等或跨边界契约，注释已经写在代码旁边，而不是只写在 PR 描述中。
- 涉及关键后端业务链路、状态流转、命令执行、事件 / 订阅、协议链路、批处理或外部 I/O 时，已确认 TraceHolder / MonoTracer / FluxTracer 埋点目标、关键属性、上下文传播和敏感信息排除；不新增埋点时有明确理由。
- 涉及常驻内存任务、缓存、队列、buffer、重试池、会话 / 连接 / 订阅管理器或后台执行器时，已确认 MBean 决策、统计指标、监控字段、安全内部操作、生命周期和敏感信息排除；不新增 MBean 时有明确理由。
- 实现中若发现长期需求、稳定契约、架构决策、验收语义或长期风险不成立，已更新任务契约、重新确认并收敛权威来源；纯实现假设或执行失败只更新运行态。
- 复杂或曾停滞的任务已按 `$systematic-solving` 与 JetLinks 扩展写清违反的不变量、共同根因或显式变化轴；bug 验证原始触发，共享行为变化验证同类代表，边界风险变化验证反例，并覆盖受影响回归；没有为了继续过测遗留无依据的特例、guard、fallback、retry、mock、兼容别名或复制实现。

门禁约束：

- 缺任务契约或缺用户确认的较大后端改动，不创建 ready for review PR。
- 发现仅为了同 PR 未发布中间形态而保留的兼容分支、旧别名、双解析、迁移代码或旧行为测试时，不创建 ready for review PR；先收敛到最终最佳实践。
- 复杂 SQL / 原生 SQL 使用特定数据库方言但未在文档和 PR 中标明风险时，不创建 ready for review PR。
- 查询形态、数据规模、索引风险、分页方式或批量规模发生变化但缺少相称的压力测试、执行计划或替代性能证据时，不创建 ready for review PR；没有性能风险变化时不触发该门禁。
- 公共类、SPI / 扩展点方法缺少完整注释，或 SPI 必要 `@since` / `@see` 版本和关联类型未确认时，不创建 ready for review PR；先补注释或写明阻塞。
- 复杂业务、权限、兼容、生命周期、TraceHolder / MBean、协议 wire、事件订阅、跨边界契约等必须注释的代码只在 PR 描述里说明、未落到代码旁边时，不创建 ready for review PR；先补代码注释或改为 draft 并写明阻塞点。
- 关键后端业务链路缺少链路追踪决策时，不创建 ready for review PR；必须说明已补 TraceHolder 埋点，或说明已有平台自动追踪覆盖 / 本次不适用的依据。
- 常驻内存任务、缓存、队列或后台执行器缺少 MBean 运维可观测性决策时，不创建 ready for review PR；必须说明已补 MBean，或说明已有 MBean / 监控覆盖 / 本次不适用的依据。
- 缺测试目标或测试目标没有映射真实业务场景的数据，只能作为 draft 或阻塞说明。
- 不允许为了达成门禁而删除测试、弱化断言、只 mock 被测核心逻辑、只跑无关模块测试或把期望值改成错误实现的输出。
- 复杂或曾停滞任务中，已改变的共享行为没有同类代表、已改变的边界没有反例证据，或仍保留无法用稳定变化轴解释的特调分支时，不创建 ready for review PR。

## 后端功能变更测试门禁

当 PR 包含后端新增功能或既有功能变动时，必须有能直接观察该变化的有效验证证据。测试类型不是固定套餐；先判断 owning boundary、可观察行为和真实风险，再选择最小充分组合。

- 新增或调整 Controller / Service / Entity / Repository / Command / Event / Subscribe / Codec 等后端行为。
- 新增接口、查询条件、权限、字典、状态流转、数据写入、副作用或跨模块调用。
- 修改协议解析、消息编解码、订阅消费、定时任务、批处理、缓存同步或异常分支。
- 修复 bug 时改变了用户可见结果、持久化数据、事件消息或对外 API 语义。

PR 前必须完成：

- 先映射已有单元、契约、集成、端到端或其他可重复验证证据；指纹与相关输入仍有效且能覆盖变化时直接复用。自动化不可用时，人工观察只能作为带明确回归风险的降级证据。
- 只有行为缺口存在时才新增或更新测试：新增能力验证主路径；bug 验证原始触发；异常、边界、权限和状态用例只覆盖本次已确认的语义 / 风险变化，不能反向创造生产 guard。
- 只有数据库 / 消息 / 事件 / 协议 / 跨模块 / 外部依赖的交互契约、真实装配、序列化、持久化或传播语义发生变化，且更低层证据不能观察时，才补集成测试。使用了这些技术本身不触发。
- 性能验证只在查询形态、数据规模、索引风险、分页方式、批量规模或资源使用发生变化时触发，选择压力测试、执行计划或能直接观察风险的替代方式。
- 仓库已有覆盖率阈值时必须满足；没有阈值时覆盖率是可选诊断信息，不为追逐数字增加无行为价值的测试。
- PR 描述列出实际使用和复用的证据、覆盖的变化行为、结果，以及仍缺失的真实风险；不要求为每种测试类型填写一个结果。

门禁约束：

- 改变的可观察行为没有任何有效证据时，不进入 ready for review；不以“必须新增单元测试”替代这一判断。
- 必要的跨边界风险只能由集成环境观察而当前无法执行时，必须标明阻塞、替代证据和剩余风险；仅当用户明确要求提前共享或远端 CI 是解除阻塞的必要条件时维护一个 draft PR。
- 未选择某类测试时无需逐项证明“不适用”；只说明实际证据与真实未覆盖风险。
- 覆盖率工具缺失且仓库没有覆盖率门槛时不是阻塞；不要用人工估算伪造数字。
- 不允许通过删除测试、注释断言、降低有效断言或只跑无关模块测试来满足门禁。

## 测试要求

提交与交付前必须确保可重复验证证据覆盖本次新增 / 改变的行为。这里要求的是“有效证据”，不是在进入 delivery 或 PR 阶段后机械重跑测试。

### 验证证据复用与失效判定

先按连贯验收切片映射已经保存的阶段验证或 CI 结果，再决定是否补跑；不要在 delivery 阶段把一个阶段拆成逐测试证据审计。可复用证据只需有稳定 locator、它证明的 acceptance slice、结果，以及被测 source / checkpoint identity。命令、工具原始计数和环境细节由原证据保留，交付说明引用即可，不重复抄写或重建。

已有证据满足以下低成本检查时直接复用：

- 它直接覆盖当前仍适用的行为 / 风险切片，结果可核验且执行未被截断或弱化。
- 当前 Source Snapshot / validated checkpoint 与被测 identity 匹配，或后续变化没有触及该切片记录的相关输入。
- 只有检查实际依赖外部环境或时效状态时，才确认对应环境、数据或远端状态仍等价。

不要仅因 commit hash 变化重新计算 tree / diff 指纹或为每个测试准备 path 影响证明。已有 continuity / CI 元数据已表明切片相关输入未变时直接引用；只有身份失配、相关路径变化或验收语义改变时，才展开该切片的命令、输入和环境细节。

出现以下任一情况时，只补跑受影响的检查，不默认扩大成全量重跑：

- 验收矩阵存在未覆盖项，证据缺失、失败、不可核验或无法定位到被测代码状态。
- 相关代码、测试、配置、依赖、构建逻辑、工具链或环境前置条件发生变化。
- base 漂移引入了与本次改动相交的变化，或 HEAD 后续提交触及该证据覆盖的输入与路径。
- 检查本身具有时效性，例如远端 CI 状态、安全 / 依赖漏洞数据、真实外部系统兼容性或发布基线检查。
- 仓库规则或用户明确要求基于最终候选 commit 重新执行某项门禁。

阶段已经集中验证并提交后，只要该阶段的相关输入未被后续阶段改动，总体验收直接引用阶段证据。创建 commit 导致 HEAD hash 改变不会单独使证据失效，也不要求在 PR 中重新证明 tree / diff 等价。禁止仅因为“现在到了交付阶段”再次运行整套单元、集成、压力或端到端测试。

优先级：

1. 识别本次新增 / 改变的可观察行为、owning boundary 与真实风险。
2. 审查已有证据的覆盖范围与指纹；仍有效的直接复用。
3. 对缺失或失效的行为证据，选择能直接观察该 owner 的最轻量测试层级。
4. 只有更低层无法观察已改变的跨边界契约或真实装配语义时，再补集成 / 端到端测试。
5. 仓库已有覆盖率门槛时，用仍有效数据或定向补跑满足；没有门槛时不为覆盖率数字造测试。

最低交付要求：

- 给出阶段 / CI 证据 locator、acceptance slice 和 source / checkpoint identity；原证据已有命令时不重复抄写
- 只列出本轮实际补跑的命令（若有）及复用或补跑判断
- 给出实际复用、新增或更新的检查及其核心覆盖点
- 测试工具能提供时给出通过数、失败数、跳过数
- 若跨边界风险需要集成测试，给出结果或明确缺失风险
- 仓库有覆盖率门槛或已有可靠数据时给出覆盖率结果

可接受的证据示例：

- `mvn -pl modules/device-manager -am test`
- `mvn -pl modules/device-manager -am verify -P integration-test`
- surefire / failsafe 报告中的 passed、failed、skipped
- jacoco 报告中的 line / branch 覆盖率
- changed files / changed classes 的 line / branch 覆盖率

不合格的说法：

- “已测试”
- “本地没问题”
- “理论上可用”

如果测试受阻：

- 明确阻塞原因，例如环境依赖、外部服务、数据库、消息中间件
- 明确已完成的替代验证
- 明确仍然存在的风险
- 未满足团队要求前，不把该提交描述为可合并状态

## 文档一致性要求

当本次改动涉及代码、配置、接口、数据结构、页面交互、枚举/字典或业务规则变化时，交付前还需要检查对应文档是否应同步更新。

文档落点先遵循 [`../../jetlinks-router/references/document-placement-rules.md`](../../jetlinks-router/references/document-placement-rules.md)。尤其注意：README 只作为仓库或模块的长期总览，不放单次测试报告、PR 描述、临时计划、排查流水或任务总结。

优先级：

1. 先判断文档类型：长期总览、功能 / API 说明、设计 / ADR、测试证据、经验沉淀，分别放到对应归属位置。
2. 先更新已有 canonical 文档，例如模块 README、功能说明、接口说明、仓库 `AGENTS.md`、既有 design / ADR / docs 索引；原位替换过时结论，README 只同步长期稳定的模块职责、入口和链接。
3. 测试命令、覆盖率、集成测试结果等证据优先放 PR 描述或 CI 报告，不新增长期测试报告文档。
4. 只有现有文档无法承载，且内容有长期复用价值和明确维护归属时，才新增独立专题文档。

约束：

- 不要在权威 docs 中为了交付“留痕”新建 task doc、active/archive 流水或归档记录；Trellis 自有 task / archive 由其生命周期维护。
- 不要为了说明本次 PR 通过了哪些测试而修改 README。
- 不要把同一功能拆成多个 plan、summary、test-report、worklog 文档；任务运行态与权威设计各有唯一归属，测试证据放 PR / CI。
- 如果当前仓库规则要求同步文档，且文档明显滞后于实现，不要把交付描述为已完成。
- 如果用户明确要求暂不补文档，或当前任务只是纯文档 / 纯评审 / 纯同步操作，需要在 PR 描述中写清原因与风险。

## PR 描述要求

PR 描述必须是结果导向，不写空话。
PR 描述必须按本文件中的推荐模板输出，标题、顺序和空行保持一致；不要改写成自由摘要，不要合并章节，不要自创主标题。仓库 `.github/pull_request_template.md` 只作为镜像同步，不是唯一来源。

至少包含：

1. 目的
2. 核心变动
3. 测试结果
4. 文档同步情况
5. 风险与未覆盖项

较大后端改动或新功能还必须包含：

- 任务契约路径与权威文档同步结论
- 用户确认状态
- 测试目标达成情况
- CRUD / AssetsHolder 数据权限分析结论（如适用）
- 数据库兼容性与 SQL 性能结论（如适用）
- 注释 / 公共契约结论（如适用）
- 链路追踪 / 可观测性结论（如适用）
- MBean / 运维可观测性结论（如适用）

## 执行提示

当用户要求“提交代码”“推送代码”“发 PR”“整理交付说明”时：

1. 先检查当前分支是否为主干或版本分支。
2. 如果是主干或版本分支，不直接 push，先创建临时分支。
3. 根据仓库历史整理合规的 commit title。
   - 如果用户要的是完整 commit message、合规审查或 shell 命令，加载 `commit-message-zh.md` 与 `shell-commit-examples.md`。
4. 如果是后端新增功能或既有功能变动，先确认 owning boundary 和已有证据是否覆盖；仅对真实行为缺口补最合适层级的测试。
5. 将已有阶段 / CI 证据映射到验收矩阵，并核对被测代码 / Git 指纹、相关输入变化、base 漂移和时效性；仍有效的直接复用。
6. 只对缺失、失败、已失效或具有时效性的行为范围定向补跑检查；按工具能力收集结果计数，覆盖率仅按仓库门槛处理。
7. 检查是否存在应同步的原始文档；若需要但尚未更新，先补文档或明确记录风险与原因。
8. 检查公共类、SPI / 扩展点方法和复杂逻辑的注释是否符合契约要求，必要时补真实 `@since` / `@see`。
9. 判断当前任务是否仍是一个清晰评审主题；如果混入独立需求，停止扩展当前任务，将额外主题拆为后续任务，而不是为当前阶段新开 PR。
10. 检查所有阶段均已验证并形成必要的本地 commits，Recovery Capsule 指向最终状态，总体验收矩阵已完成。
11. 如果远端是 GitHub，先检查 `gh auth status`；当前工具支持非沙箱审批时使用非沙箱执行，不支持时说明限制并按可用方式降级。
12. 生成 PR 标题与 PR 描述，确保包含目的、核心变动、阶段 commits、测试数据、文档同步情况和风险说明。
13. 创建 PR 前，确认用户认为任务已完成。
14. 统一 push 临时分支后，优先使用 `gh pr create` 创建一次 ready for review PR；任务未完成时默认不执行远程交付，只有显式中间共享例外才更新同一个 draft PR。
